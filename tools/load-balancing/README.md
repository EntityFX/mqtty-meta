# Сравнение одного и трёх MQTT-брокеров

`study.py` выполняет отдельное исследование в MqttY и строит Markdown-отчёты. Настоящие брокеры не запускаются: первая часть использует идеальную модель через `demo`, вторая — замороженный профиль Mosquitto через `run`. Существующие результаты кампании не изменяются.

## Программа

| Часть | Варианты | Число запусков |
| --- | --- | ---: |
| Demo | Single N=16, N=48, N=64; directBalanced, RR, LC с тремя backend по 16 publishers | 6 × 2 нагрузки × 3 QoS × 3 seeds = 108 |
| Mosquitto | Single N=16, N=64; directBalanced, RR, LC с тремя backend по 16 publishers | 5 × 2 нагрузки × 3 QoS × 3 seeds = 90 |
| Повторение | Шесть заранее выбранных точек из сохранённых run-config.json | 6 |

Payload — 16 байт; нагрузки 1000 и 60 000 сообщений/с; seeds 42, 43, 44. Warmup / measurement / drain: 0.01 / 0.2 / до 1 модельной секунды, tick 0.1 мс. Фиксированная сеть одинакова у сравниваемых вариантов; её параметры сохраняются в `study-plan.json` до первого запуска. Длительность расчёта на настоящем компьютере зависит от его ресурсов.

В профиле Mosquitto нет N=48. Поэтому **в профилированной части одновременно меняются число backend, число publishers и выбранная точка профиля**. Сопоставление single16 с пулом показывает совместный эффект, а single64 — дополнительный контроль с большим числом клиентов у одиночного брокера. Эти данные не выделяют чистый эффект трёх реальных брокеров. Для строгого сравнения 48 против 3×16 нужна отдельная натурная точка N=48 и её независимая проверка. Интерполяция и подмена N не применяются.

Стратегии исследуются на постоянных одинаковых сессиях. RR, LC и directBalanced дают одинаковые назначения; отсутствие различий — ожидаемый результат контроля, а не недостаток отчёта. Чтобы различить стратегии, понадобится отдельная программа с неодинаковой продолжительностью/весом сессий и проверкой исходов.

## Запуск на другой машине

Нужны .NET SDK, .NET 6 runtime и Python с Matplotlib. Команды выполняются из корня мета-репозитория, где доступны опубликованные профиль и калибровочные observations Mosquitto. Путь `/data/mqtt/study-new` замените новым каталогом на подготовленном диске данных.

```text
dotnet build mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.LoadBalancing.App -c Release
python -m pip install matplotlib
python -m unittest discover -s tools/load-balancing -p test_study.py -v
python tools/load-balancing/study.py run --work-dir /data/mqtt/study-new
python tools/load-balancing/study.py verify --work-dir /data/mqtt/study-new
python tools/load-balancing/study.py report --work-dir /data/mqtt/study-new
python tools/load-balancing/summarize.py --work-dir /data/mqtt/study-new
```

Перед стартом source MqttY должен быть закоммичен и чист. Программа проверяет связь observations с профилем по SHA-256 и наличие точных N=16/N=64. Исходные профиль, observations, исполняемые DLL и сам сценарий сохраняются однократно в evidence. На каждом запуске сверяются commit/чистота MqttY и исполняемые файлы. Приложение исполняется из своего build-каталога, чтобы manifest правильно определил репозиторий исходников; копия runtime сохранена для переноса.

Если серия закончена или прервана между точками, повтор команды `run` проверит seals и продолжит неполное покрытие без перезаписи успешных данных. Прерванный каталог отдельной попытки сохраняется и требует разбора; частичные файлы автоматически не удаляются. На диске должно оставаться не менее 5 ГиБ перед очередной точкой. Для этой программы ожидается несколько сотен МиБ распакованных данных; фактический размер зависит от сохранённого runtime и профилей.

## Результат

Рабочий каталог содержит точный план, configs, команды, stdout/stderr, checkpoint, полные per-run артефакты, шесть повторов и исходные байты входов. Каждый запуск приложения имеет SHA-256 registry. `verify` пересчитывает RPS, учёт уникальных сообщений и drain, знаменатели failure/loss, суммы backend и квантили по объединённым гистограммам.

В `reports/` создаются `Load-balancing-demo.md` и `Load-balancing-Mosquitto.md`. В `reports/data/load-balancing-study-v1/` — компактные scientific summaries, CSV, агрегаты, проверка равенства стратегий, сведения о повторах и четыре SVG-графика. Таблицы и графики читают одни сохранённые числа.

`summarize.py` повторно строит эти материалы, проверяет конфиги, профильные ключи и реальные файлы всех шести повторов, затем добавляет общий `Load-balancing-study.md` с интерпретацией. SVG получают стабильные идентификаторы и не содержат календарной даты генерации. Основной исполняемый протокол `study.py` остаётся замороженным во время серии; отдельный скрипт интерпретации не меняет параметры моделей.

`topologies.py`, вызываемый генератором, строит пять SVG-топологий из фактически выполненных вариантов: demo single48 и пул; Mosquitto single16, single64 и пул. Сверяются GraphML, физические связи, число клиентов и серверов, принадлежность узлов сегментам; назначения берутся из manifest. В подробные Markdown добавляются SVG и Mermaid-код пула, рядом сохраняются `.mmd` для редактирования и `topology-verification.json`. На диаграммах receivers остаются в общем клиентском сегменте, а политика назначения показана отдельно от сетевого пути.

Среднее ± t-CI95 по трём seeds характеризует только разброс модели при фиксированном профиле. Оно не учитывает натурную неопределённость или ошибку модели. Goodput делится на время нагрузки и включает drain измерительной когорты; p99 QoS 0 ACK неприменим. Короткий опыт не доказывает стационарную точность. CPU/RSS, реальный TCP proxy и EST не моделируются.

## Архив доказательств

```text
python tools/load-balancing/study.py archive --work-dir /data/mqtt/study-new --archive-path /data/mqtt/study-new.tar.gz
```

Архив должен располагаться вне исходного каталога и иметь новое имя. После создания каждый файловый член читается обратно и сравнивается по SHA-256 с исходником. Рядом сохраняется квитанция. Архив переносится на диск доказательств; перед записью на Linux нужно подтвердить, что целевой диск действительно смонтирован, и проверить хэш после переноса. Автоматического удаления исходников нет. Архивы не добавляются в Git.
