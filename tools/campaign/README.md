# Сценарии управления экспериментами

Для нового стенда начните с [руководства запуска](../../docs/full-campaign-runbook.md). Здесь перечислены назначения скриптов; исторические сценарии продолжения не заменяют подготовку новой серии.

## Подготовка и запуск

| Скрипт | Назначение |
| --- | --- |
| `portable-linux.py` | Подготовить описание нового Linux-стенда, запустить предварительную проверку, полную серию или проверку архивов |
| `compact-campaign.py` | Создать и выполнить отдельную сокращённую программу с ограничением времени |
| `launch-compact.py` | Запустить подготовленный контроллер ограниченной серии через пользовательскую службу systemd |
| `accelerated-resume.py` | Продолжить совместимую прежнюю серию с несколькими независимыми процессами симуляции |

Версии программ, параметры и пути фиксируются до запуска. Изменение файла в рабочем репозитории не обновляет уже работающий контроллер: он использует сохранённую копию кода.

Реальные измерения идут последовательно. Одновременно могут вычисляться несколько симуляций, если хватает памяти; они не должны пересекаться с натурной нагрузкой. Число процессов не меняет заданное время внутри модели.

## Переход между версиями

`service-revision-handoff.py`, `repair-campaign-handoff.py` и `relay-concurrency-handoff.py` обслуживают конкретные переходы прежних серий. Они дожидаются безопасной границы и записывают историю изменения. Перед применением нужно проверить совместимость исходной серии и назначения.

Переносится только разрешённый набор с сохранённым происхождением. Нельзя выдать результаты старой модели за результаты новой или дополнить неполные измерения данными по изменённой методике без отдельного описания.

История: [обновление модели](../../reports/history/service-budget-linux-deployment.md), [исправление телеметрии](../../reports/history/instrumentation-repair-20261018.md).

`extend-campaign-deadline.py` продлевает срок работающей ограниченной серии после явного решения сотрудника. Его запускают отдельной службой, чтобы он дождался отсутствия активных заданий. Затем сценарий проверяет владельца контроллера, неизменность файлов и профилей, сохраняет прежнее состояние и продолжает ту же серию. Простой правки `series.json` недостаточно: работающий контроллер уже прочитал прежний срок.

Сценарий принимает `--series`, новый срок с часовым поясом в `--deadline`, новый каталог истории внутри контроллера в `--audit` и причину `--reason`. Статус `waiting-for-idle-boundary` означает ожидание; только `extended` подтверждает, что новый контроллер прочитал срок. История содержит старый и новый предел, имена служб и контрольные суммы профилей. Проверки: `python -m unittest discover -s tools/campaign -p test_deadline_extension.py -v`.

## Подготовка отчётов

| Скрипт | Назначение |
| --- | --- |
| `publish-broker-reports.py` | Сохранить небольшой снимок завершённых результатов и подготовить публикацию в корневой папке `reports` |
| `write-overnight-aedes-report.py` | Повторно рассчитать таблицы завершённого цикла Aedes из синхронизированного каталога серии |
| `analyse-campaign.py` | Подготовить анализ доступных этапов серии |
| `audit-delivery.py` | Проверить учёт публикаций и получений по ID из исходного архива |

Зависимости публикации перечислены в `MqttBenchmark/scripts/campaign/requirements.txt`. Для уже сохранённого снимка:

```bash
python tools/campaign/publish-broker-reports.py --output reports
```

Скрипт проверяет хэши входов, число повторов и формулу доверительного интервала. Он создаёт таблицы и графики частичных отчётов, затем HTML трёх опубликованных брокеров. Полный текст Aedes редактируется отдельно; его исходные таблицы сохраняются.

Сбор нового снимка:

```bash
python tools/campaign/publish-broker-reports.py \
  --source <каталог-controller> \
  --evidence-root <корень-доступных-материалов> \
  --output <новый-каталог-публикации>
```

Этот издатель рассчитан на текущую полную ночную программу: 72 запуска на этап, натурная нагрузка 20 секунд, модельная — 2 секунды. Он не является универсальным генератором для любого протокола. При иной программе нужно обновить шаблон и проверки, а не только заменить пути.

Существующий снимок не перезаписывается. Подробные журналы сообщений остаются в архивах на диске результатов. Копирование итоговых файлов не считается повторным восстановлением всех архивов.

## Что считать успешным

Успешный процесс, полный набор запусков и точная модель — три разных результата. Коды возврата, журнал технических ошибок и критерии точности проверяют отдельно. Нарушения точности сохраняют; профиль и допуски по ним автоматически не меняют.

После изменения способа вычисления повторите несколько одинаковых модельных конфигураций и сравните численные итоги. Служебные даты могут различаться. Проверка нескольких сценариев подтверждает только эту выборку, а не все возможные нагрузки.
