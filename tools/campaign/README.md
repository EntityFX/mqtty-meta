# Сценарии управления экспериментами

Для нового стенда начните с [руководства запуска](../../docs/full-campaign-runbook.md). Здесь перечислены назначения скриптов; исторические сценарии продолжения не заменяют подготовку новой серии.

Связи контроллера с MqttBenchmark и MqttY, основные классы и объём исходников приведены в [архитектуре проекта](../../docs/architecture.md).

## Подготовка и запуск

| Скрипт | Назначение |
| --- | --- |
| `portable-linux.py` | Подготовить описание нового Linux-стенда, запустить предварительную проверку, полную серию или проверку архивов |
| `compact-campaign.py` | Создать и выполнить отдельную сокращённую программу с ограничением времени |
| `launch-compact.py` | Запустить подготовленный контроллер ограниченной серии через пользовательскую службу systemd |
| `accelerated-resume.py` | Продолжить совместимую прежнюю серию с несколькими независимыми процессами симуляции |

Версии программ, параметры и пути фиксируются до запуска. Изменение файла в рабочем репозитории не обновляет уже работающий контроллер: он использует сохранённую копию кода.

Реальные измерения идут последовательно. Одновременно могут вычисляться несколько симуляций, если хватает памяти; они не должны пересекаться с натурной нагрузкой. Число процессов не меняет заданное время внутри модели.

## Переход между версиями

`service-revision-handoff.py`, `repair-campaign-handoff.py` и `relay-concurrency-handoff.py` обслуживают конкретные переходы прежних серий. Они дожидаются безопасной границы и записывают историю изменения. Перед применением нужно проверить совместимость исходной серии и назначения.

Переносится только разрешённый набор с сохранённым происхождением. Нельзя выдать результаты старой модели за результаты новой или дополнить неполные измерения данными по изменённой методике без отдельного описания.

История: [обновление модели](../../reports/history/service-budget-linux-deployment.md), [исправление телеметрии](../../reports/history/instrumentation-repair-20261018.md).

`extend-campaign-deadline.py` продлевает срок работающей ограниченной серии после явного решения сотрудника. Его запускают отдельной службой, чтобы он дождался отсутствия активных заданий. Затем сценарий проверяет владельца контроллера, неизменность файлов и профилей, сохраняет прежнее состояние и продолжает ту же серию. Простой правки `series.json` недостаточно: работающий контроллер уже прочитал прежний срок.

Сценарий принимает `--series`, новый срок с часовым поясом в `--deadline`, новый каталог истории внутри контроллера в `--audit` и причину `--reason`. Статус `waiting-for-idle-boundary` означает ожидание; только `extended` подтверждает, что новый контроллер прочитал срок. История содержит старый и новый предел, имена служб и контрольные суммы профилей. Проверки: `python -m unittest discover -s tools/campaign -p test_deadline_extension.py -v`.

## Подготовка отчётов

Итоговая публикация находится в корневом `reports`. Для её пересчёта из сохранённых данных:

```bash
python -m pip install -r tools/campaign/report-requirements.txt
python tools/campaign/render-final-reports.py --output reports
python -m unittest discover -s tools/campaign -p test_final_reports.py -v
```

Генератор проверяет хэши опубликованных JSON, 576 натурных результатов, средние и CI95, 936 модельных итогов, сохранённые хэши профилей и критерии. ZIP для пересчёта не требуются. Дополнительный параметр `--archive-root <каталог-архивов>` включает проверку семи внешних архивов по SHA-256 и сверку исходных конфигураций, manifests и counters всех моделей. Затем создаёт четыре полных брокерных отчёта, смешанную сеть, сравнение с EST\*, микроотчёт и документ о проверке модели; таблицы, графики и автономные HTML вычисляются из одного набора данных. EST\* и анализ чувствительности описаны в [сравнении](../../reports/Broker-comparison.md). CPU берётся из внутренних интервалов нагрузки, а не из захвата с простоем.

| Скрипт | Назначение |
| --- | --- |
| `collect-final-evidence.py` | Собрать завершённую серию в новый каталог, проверить seals прочитанных членов raw ZIP, сохранить параметры и доказательства всех моделей |
| `render-final-reports.py` | Проверить снимок и воспроизводимо вычислить итоговые документы, графики и EST\* |
| `replay-final-models.py` | Повторить шесть заранее выбранных моделей с исходными config и замороженным runtime; проверить summary, научные counters, histogram и фазы |
| `publish-broker-reports.py` | Прежний сборщик частичной публикации; его функция collect также используется итоговым сборщиком. Не применять прежний renderer к финальному reports |
| `analyse-campaign.py` | Подготовить рабочий анализ доступных этапов на стенде |
| `write-overnight-aedes-report.py` | Генератор прежнего отдельного отчёта Aedes |
| `audit-delivery.py` | Проверить учёт публикаций и получений по ID |
| `diagnose-activemq.py` | Проверить 144 результата ActiveMQ и подробно пересчитать 24 выбранных raw-архива |
| `probe-activemq-duration.py` | Сравнить модельные окна 2 и 10 с с прежним профилем и DLL |
| `write-activemq-diagnosis.py` | Пересоздать отдельный диагностический отчёт ActiveMQ |

Сбор нового финального снимка:

```bash
python tools/campaign/collect-final-evidence.py \
  --source <controller> \
  --evidence-root <корень-mqtty-evidence> \
  --output <новый-каталог-публикации>
```

Сборщик рассчитан на завершённую overnight-v1: 72 запуска на этап, измерение 20 с, модель 2 с. Он сопоставляет сохранённые абсолютные пути этой серии с доступным корнем evidence. Для другой программы нужны явные изменения проверок. Копируются агрегаты, сведения о происхождении, выбранные sealed members и компактные архивы модельных файлов; большие журналы сообщений остаются на диске результатов. Полное повторное чтение всех raw ZIP при сборе не выполняется; квитанции прежнего восстановления сохраняются отдельно.

В итоговом снимке также нужны `data/article-sources.json` (имена, SHA-256 и численные EST-таблицы авторских DOCX), `data/replay-results.json` и реестр `data/external-archives.json`. ZIP остаются на диске результатов и исключаются из Git; реестр содержит пути, размеры и SHA-256. Опубликованные JSON входят в `data/final-evidence-sha256.json`, хэши внешних архивов отделены от файлов репозитория. Повторения выполняются отдельной командой на Linux после завершения кампании:

```bash
python tools/campaign/replay-final-models.py \
  --controller <controller> --output <новый-каталог-повторов> --dotnet <dotnet>
```

Для публикации этой серии шесть повторений выполнены 19 октября; сравнение научных частей counters сделано отдельно после выполнения, а исходный протокол сохранён внутри replay-evidence.zip. Полный counters содержит строку с реальным временем, поэтому не обязан совпадать целиком. Повторения не увеличивают основное покрытие и не являются новой независимой проверкой точности.

## Что считать успешным

Успешный процесс, полный набор запусков и точная модель — три разных результата. Коды возврата, журнал технических ошибок и критерии точности проверяют отдельно. Нарушения точности сохраняют; профиль и допуски по ним автоматически не меняют.

После изменения способа вычисления повторите несколько одинаковых модельных конфигураций и сравните численные итоги. Служебные даты могут различаться. Проверка нескольких сценариев подтверждает только эту выборку, а не все возможные нагрузки.
