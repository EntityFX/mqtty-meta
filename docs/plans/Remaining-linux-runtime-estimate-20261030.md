### Основание оценки кампании

Два последовательных набора A стоят примерно2×177,903=355,805с. Если два B-набора с workers2 занимают каждый90–180с,ABBA потребует536–716с=8,9–11,9мин без дополнительной упаковки/проверки. С запасом получается10–15мин. Это **не прогноз измеренного speedup**: предположение о B нужно проверить,ускорение может отсутствовать. Жёсткий20-минутный срок включает запас и не гарантирует принятых результатов.

### Суммарно

- Первые два пункта: **25–60мин расчётов**; предлагаемый объединённый hard budget≤80мин после готовности кода.
- Первые четыре пункта на нынешнем Linux: **81–185мин**,то есть примерно**1ч20мин–3ч05мин** расчётов и проверок. Сумма предлагаемых отдельных hard limits245мин=**4ч05мин**. Это не обещание завершения до3часов; задача до/после остаётся недостаточно определённой.
- Дополнительно другая машина и настоящая сеть: ещё**50–115мин чистых прогонов** после подготовки. Общая оценка всех шести при готовых средствах —**2ч11мин–5ч**. Разработку и настройку стендов в этот итог включать нельзя без отдельной оценки.

## Порядок исполнения и стоп-условия

1. Подготовить и проверить кампанию,затем benchmark ядра; не запускать одновременно разные исследуемые схемы и внешнюю нагрузку.
2. Для до/после сначала проверить два commits и короткий sizing; при несовпадении результатов не запускать полную матрицу и не выбирать только успешные случаи.
3. Новый хвост4096 не считать обязательным для уже объявленного40-секундного наблюдения. Если он запускается,его новый срок фиксируется до запуска; прежняя частичная попытка сохраняется.
4. Второй физический стенд и настоящую сеть не заменять модельным прогоном или сменой SSH-контроллера.
5. Каждый job/блок имеет абсолютный deadline,сохраняет failures и не делает автоматический retry. После подтверждения долгого фонового запуска обновить Progress.md и остановиться для ожидания.

Общий исходный прогресс53,2%,общая подготовка80%. Предварительная оценка времени не является выполненным экспериментом и не повышает процент.
