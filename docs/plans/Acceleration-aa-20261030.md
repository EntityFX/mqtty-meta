# Проверка измерителя ускорения кампании — Implementation Plan

**Goal:** выполнить первый разрешённый пункт: ограниченную A/A-проверку перед сравнением workers1/2.

**Architecture:** отдельный Python supervisor, GNU time для user/system CPU и peak RSS каждого child, общие /proc-снимки RSS и cgroup-счётчики. Используется неизменённый q1024 и frozen runtime сети. Два последовательных набора по две одинаковые модели; исходы каждой попытки сохраняются.

**Tech Stack:** Python standard library, Linux cgroup v2, GNU time, systemd user service.

**Spec:** [программа ускорения](../dissertation/acceleration-benchmark-20261030.md).

## Ограничения и проверка

- Отдельный бюджет 600 с: RuntimeMaxSec595 + TimeoutStopSec5, вычисления до480 с, далее проверка/завершение. Без retry, автопродолжения и изменения fixture.
- CPU affinity4,6, CPUQuota200%, MemoryMax6G, swap0; оба набора используют одну политику. Если CPU недоступны, запуск не допускается.
- Cold process/JIT входит в wall; файловый cache не сбрасывается. Это одинаковая политика обычного файлового cache, а не утверждение о холодном диске.
- A/A — четыре модели, **не** измерение speedup. Primary wall каждого набора включает проверку двух результатов. Все шесть научных файлов должны совпасть во всех четырёх моделях.
- Разброс A/A: abs(wall1−wall2)/min(wall1,wall2). При >=10% следующий численный benchmark не допускается без отдельного решения; дополнительные повторы автоматически не добавляются.
- Сумма отдельных peak RSS и максимум одновременно наблюдённого RSS сохраняются раздельно. Время CPU контроллера и cgroup также раздельно.
- При timeout, nonzero, несовпадении научных файлов, ресурсном отказе или ошибке пересчёта остановить блок, сохранить причину. Kill только принадлежащих supervisor process groups; общий systemd контролирует потомков.
- Во время опыта не запускать Web jobs или другие benchmarks. Основной LaTeX и все исторические входы сохраняются.
