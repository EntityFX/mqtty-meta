# Приёмка окончательного профиля через Linux Web

Используются существующий план одиночной проверки, writing-plans и verification-before-completion. Это техническая проверка оболочки, не новая серия оценки точности.

## Заранее заданная программа

1. Принять завершённую короткую пару очередей отдельно; не повторять её и не менять нагрузку автоматически при отсутствии переполнения.
2. Проверить освобождённый порт 5088 и отсутствие незавершённых заданий. После перезагрузки диск hd250 подключить, сохранив все исходные каталоги. Для переноса данных сначала использовать чтение; запуск Web требует записи только в его рабочие каталоги и новый релиз.
3. Проверить три существующих теста TwinValidation. Опубликовать неизменённый mqtty commit `4c658536586f88a89cd3ff5ab0915903640cf3c9` в новый каталог с SHA каждого файла; старые релизы и frozen runtime основной серии сохраняются.
4. На Linux ограничить Web одним worker, 2 ГиБ памяти и 150% CPU через существующий host. Стартовать только остановленную службу, живые процессы не перезапускать. Предварительно проверить размер данных и свободное место.
5. Создать отдельные пользовательские пресеты для четырёх окончательных профилей из серии 40/40. Подготовить побайтные копии профилей в рабочем каталоге Web, затем зарегистрировать пресеты через API; сохранить SHA и исходные идентичности. Пресеты по умолчанию не менять. Проверить через API точный режим 16 байт / QoS 1 / 16 publishers и отрицательный случай с отсутствующим числом publishers. Отклонение изменённого профиля проверяется существующим тестом адаптера: публичный API сам вычисляет SHA и не принимает заявленный пользователем SHA отдельным полем. Это подготовка входов файловым копированием, не проверка браузерной загрузки профиля.
6. Исполнить через API ровно один короткий опыт Aedes: seed 42, прогрев 0,01 с, подача 0,1 с, дополнительное наблюдение 0,1 с, tick 10 мкс. Aedes выбран как первый по порядку брокер серии, не по результату точности. Предел задания 120 с, общий предел этой проверки 600 с, автоматического retry нет.
7. Исполнить тот же вход сохранённым прямым Probe основной серии в новом каталоге с теми же пределами и сравнить научные результаты, ID, payload, гистограммы и фазы. Исходные профили и runtime не переписывать. Различия служебной идентичности или сериализации не выдавать за полное побайтовое совпадение.
8. Сохранить HTTP-ответы, состояние задания, все попытки и точные расхождения. Не считать доступность страницы доказательством выполнения модели. При отсутствии отдельного натурного эталона Web не получает отметку независимой точности.

## Границы

- Это путь API → очередь Web → отдельный процесс → результаты, не полный браузерный приёмочный сценарий всех экранов.
- Окна сокращены для технической проверки; результаты не добавляются к основным 40 исполнениям и не заменяют сравнение с натурным контролем.
- Отрицательные проверки не изменяют исходные профили. Существующие результаты и история не удаляются.
- Нет циклического опроса научных служб и новых таймеров. Короткое ограниченное ожидание конкретного API-задания допускается внутри 600 с; долгий расчёт не запускать.
- Основной текст диссертации редактирует только автор. Агент сохраняет отдельный отчёт и обновляет Progress.md.
