# План подпроекта MqttY: балансировка MQTT-соединений

## 1. Цель и статус

Добавить в MqttY самостоятельное приложение для исследования распределения подключений между брокерами сообщений. Сравнить один брокер, заранее распределённый пул и назначение подключений по Round Robin и Least Connections.

**Первая версия реализована в отдельном проекте существующего solution.** Ниже сохранены программа исследования и критерии проверки. Первой версией исследуется выбор backend для долгоживущей MQTT-сессии. Модель не описывает внутреннюю работу реального HAProxy/Nginx, стоимость TCP-proxy, CPU или задержку принятия решения балансировщиком.

Принятые ограничения:

- Добавить **один проект**, без нового solution и без нового тестового проекта.
- Расширять MqttY; сохранить поведение существующих BrokerFidelity, MqttRelay и прежних команд.
- Использовать действующие публичные средства построения сети, профили и счётчики.
- Код должен иметь понятные обязанности и небольшие зависимости. Не создавать DI-контейнер, универсальный plugin framework или дополнительные слои ради структуры.
- Полноценный proxy, динамическая миграция сессий, health checks, failover и объединение брокеров через Relay в v1 не входят.

Политика не пишет файлы и не управляет временем; writer не принимает решений о маршрутизации; runner не вычисляет стратегию внутри протокольного обработчика.

## 3. Модель подключения

1. Сформировать стабильный порядок publisher-клиентов и backend.
2. Для каждого publisher выбрать backend **до CONNECT**.
3. Сразу зарезервировать подключение, не дожидаясь CONNACK. Иначе параллельная партия Least Connections может целиком выбрать первый брокер.
4. Подключить клиента и сохранить карту `publisher → backend` на весь опыт.
5. При ошибке подключения завершить опыт с диагностикой. Скрытую повторную балансировку не выполнять.
6. Подключить один receiver напрямую к каждому backend и подписать его на измерительную тему. Эти служебные соединения не участвуют в выборе backend для publishers.

| Режим | Правило |
| --- | --- |
| single | Все publishers подключены к одному backend |
| directBalanced | Карта заранее задана циклически; выбора backend при подключении нет |
| roundRobin | Следующее подключение направляется следующему backend по циклу |
| leastConnections | Выбирается минимум зарезервированных publisher-соединений; при равенстве — первый backend в заданном порядке |

Для v1 все сессии постоянны, одинаковы по весу и не мигрируют. В однородном пуле RR и Least Connections могут дать одинаковую карту и результаты. Это ожидаемый контроль, а не свидетельство преимущества одного алгоритма. Исследование разных длительностей сессий и неодинаковых весов потребует отдельной программы.

### Семантика доставки

Receiver проверяет публикации, созданные publishers его backend. Публикация брокеру A не должна автоматически появляться у подписчика брокера B. Балансировщик соединений не объединяет подписки и не создаёт общую MQTT-сессию для независимых брокеров.

Результаты относятся к суммарной локальной доставке распределённых потоков. Их нельзя представлять как доставку произвольному единому подписчику через кластер. Отрицательный тест межброкерной доставки обязателен.

## 4. Топология и профили

Использовать одинаковый клиентский сегмент, одинаковое число сетевых участков до backend и одинаковые параметры каждого канала. Новый проект создаёт граф через публичный `MqttNetworkBuilder`, как самостоятельные примеры MqttY. Существующий runner, который подключает publisher к серверу собственной области, не изменяется.

Параметры профиля выбирать по фактическому количеству **publishers конкретного backend**. Receivers и прочие соединения к этому числу не прибавляются. В manifest сохраняются назначения и точный ключ профиля.

Особенности текущей реализации:

- `BrokerProfileSet` читает и хэширует snapshot профиля, сохраняет provenance и проверяет совместимость.
- Эмпирический v4 требует наблюдавшееся число publishers. Неподдерживаемое N нельзя заменить ближайшим или молча интерполировать.
- `MqttBroker` является internal; создавать его нужно через существующий builder, а не открывать класс только ради нового app.
- EmpiricalServiceBudget в действующем эксперименте разрешён только одиночному BrokerFidelity. Новый пул не наследует этот режим и его результаты точности автоматически.
- Публичный `MqttClient.HasPendingPublish` позволяет контролировать наличие незавершённого обмена QoS 1/2. Метрики backend доступны через `IMqttBroker.GetMetrics()`.

Порядок проверки: сначала вычислить карту назначений, затем проверить наличие всех `(brokerType, payloadBytes, QoS, publishersOnBackend)`, после этого создавать граф. Для v1 конфигурации с backend без publishers отклонять; поддержка пустых backend не нужна для согласованной матрицы.

В исследовательской матрице используются точные точки существующего полного профиля: single — N=64, четыре backend — N=16 у каждого. Профили сокращённого протокола без N=64 для этой матрицы не подходят.

## 5. Настройки и команды

Входные пути разрешать относительно файла конфигурации. Это правило нового приложения; оно не изменяет разрешение путей в прежнем experiment CLI.

Минимальный формат новой конфигурации:

```json
{
  "schemaVersion": 1,
  "mode": "roundRobin",
  "brokerType": "Aedes",
  "backendCount": 4,
  "brokerProfilePath": "reports/data/Aedes/profile/broker-calibration.v3.json",
  "ideal": false,
  "totalPublishers": 64,
  "payloadBytes": 16,
  "publishQos": 1,
  "subscribeQos": 1,
  "offeredRps": 20179.382680945022,
  "seed": 42,
  "warmupSeconds": 1,
  "measurementSeconds": 2,
  "drainTimeoutSeconds": 5,
  "tickPeriod": "00:00:00.0001000",
  "networkLength": 2,
  "network": {
    "capacityBytesPerSecond": 125000000,
    "throughputWindowTicks": 100,
    "queueCapacity": 100000,
    "transferTicks": 2
  }
}
```

Этот пример предполагает сохранение `load-balancing.local.json` в корне мета-репозитория. Значение offeredRps взято из средней attempted RPS калибровочной точки Aedes, 16 байт, QoS 1, N=64. Имя файла профиля историческое; фактическую версию схемы читает загрузчик.

Ёмкость и очередь сети — явно заданные допущения. Внешняя offeredRps — суммарная по всем publishers, а не скорость каждого backend. Параметры одной сравниваемой группы не подбираются по получившемуся результату.

При `ideal=true` профиль не применяется и поле brokerProfilePath должно отсутствовать. Такой режим нужен для проверки алгоритма и учёта; его результаты не являются результатами двойника настоящего брокера.

### Интерфейс приложения

- `validate --config <json>`: проверить входы, вывести карту подключений, ключи профилей и длительности; симуляцию не запускать.
- `run --config <json> --output <new-directory>`: выполнить одну конфигурацию и сохранить доказательства.
- `matrix --config <json> --output <new-directory>`: сформировать и выполнить определённую ниже матрицу. Параметры одной точки из примера разворачиваются по правилам матрицы.

Для `matrix` конфигурация дополнительно содержит массив `brokerProfiles` из четырёх записей с полями `brokerType`, `brokerProfilePath`, `calibrationObservationsPath`. Порядок: Aedes, Mosquitto, ActiveMQ, EMQX. Поле одиночного brokerProfilePath при этом отсутствует. Интенсивности вычисляются из калибровочных observations, проверенных на соответствие происхождению выбранного профиля. Контрольные observations для выбора нагрузки не используются.

Команды из корня мета-репозитория:

```powershell
dotnet build mqtty/src/EntityFX.MqttSimulator/EntityFX.Mqtty.sln -c Release
dotnet mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.LoadBalancing.App/bin/Release/net6.0/EntityFX.MqttY.LoadBalancing.App.dll validate --config load-balancing.local.json
dotnet mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.LoadBalancing.App/bin/Release/net6.0/EntityFX.MqttY.LoadBalancing.App.dll run --config load-balancing.local.json --output D:/mqtt-results/load-balancing-one
```

Путь результата заменяется путём на подготовленный диск данных. В Linux вместо PowerShell используются те же вызовы dotnet из Bash. Готовый конфиг одиночной точки находится в `docs/examples/load-balancing/aedes.json`, профилированной матрицы — в `docs/examples/load-balancing/matrix.json`, идеальной проверки — в `mqtty/doc/examples/load-balancing/ideal.json`. Пример команд выше предполагает отдельный `load-balancing.local.json` в корне, как указано перед примером JSON.

Коды завершения: 0 — предусмотренные фазы завершены; 1 — неверные входы; 2 — технический отказ или незавершённый drain. Код 0 не означает натурную точность модели. Существующий каталог результата не перезаписывается. При техническом отказе уже полученная диагностика сохраняется.

## 6. Нагрузка и границы учёта

Внутри одного опыта обновление последовательное. Длительности переводятся в целое число ticks с проверкой совместимости; невозможные значения отклоняются до исполнения.

Внешние публикации распределяются между publishers равномерно, с сохранением дробной части интенсивности. Для QoS 1/2 один publisher не начинает следующую публикацию, пока предыдущая ожидает подтверждения. Задержку из-за backpressure учитывать отдельно от фактического вызова Publish. Для QoS 0 подтверждения нет.

В реализации используются собственные слоты каждого publisher с ограниченным запасом `ceil(offeredRps × tickSeconds / totalPublishers)+1`. Занятый отправитель не передаёт нагрузку свободному. Разность scheduled−apiAttempts включает вытесненные слоты и остаток к концу measurement. Для защиты от ошибочной конфигурации v1 разрешает payload 16/256 байт, до миллиона запланированных публикаций, 4096 publishers, 64 backend и 1024 сетевых участков backend на опыт. Эти ограничения не заменяют проверку ресурсов pilot-прогоном.

Точный порядок фаз:

```text
проверка входов и карты назначений
→ построение сети
→ подключения publishers и receivers
→ подписки
→ прогрев
→ начало измерительной фазы и сброс предусмотренных счётчиков
→ подача нагрузки
→ прекращение новых публикаций
→ drain до завершения работы либо заданного предела
→ сохранение результата
```

Каждый payload содержит 16-байтовый заголовок: 8 байт уникального ID и 8 байт модельного tick отправки, в little-endian. Для payload 256 байт оставшаяся часть дополняется до заданной длины. ID уникален в пределах опыта, включая прогрев. Ledger связывает его с publisher, backend и фазой. Клиент публикует исходные байты, receiver читает их через существующее событие MessageReceived.

Только ID, созданные во время measurement, входят в измерительные попытки и уникальные доставки. Получение таких сообщений в drain сохраняется отдельно; сообщения прогрева и дубликаты не увеличивают unique goodput.

Нужно различать два уровня счётчиков:

| Уровень | Источник | Что означает |
| --- | --- | --- |
| Отправители и receivers нового app | Собственный DeliveryLedger | Вызовы отправки, отказ метода Send/Publish, уникальные ID, получения, фаза и сквозная задержка |
| Backend MQTT | Существующие BrokerMetricsSnapshot | Допуски, завершения, rate rejection, модельные ошибки, ожидаемые выдачи и гистограммы завершения |

У текущего публичного API нет готового по-ID реестра конечных исходов публикаций. Поэтому новый app не должен выводить, что каждое исчезновение HasPendingPublish означает успешный ACK, или вычислять условную потерю «среди завершённых ID» без соответствующих наблюдений. V1 использует готовые backend-метрики для завершений и их задержек, а ledger — для сквозных получений. Изменение ядра ради такого нового наблюдателя в этот этап не входит.

## 7. Матрица первичного исследования

| Параметр | Значение |
| --- | --- |
| Типы брокеров | Aedes, Mosquitto, ActiveMQ Classic, EMQX |
| Состав пула | Однородный, четыре backend одного типа |
| Режимы | single, directBalanced, roundRobin, leastConnections |
| Publishers | 64 всего; single — 64, пул — 16 на backend |
| Payload | 16 байт |
| QoS публикации и подписки | 0, 1, 2; одинаковые в одной точке |
| Seeds | 42, 43, 44 |
| Warmup / measurement / drain | 1 / 2 / до 5 модельных секунд |
| Tick | 100 мкс |
| Транспорт | Фиксированный и одинаковый между сравниваемыми режимами |
| Нагрузка | attemptedRps калибровочной точки данного типа, payload 16, QoS, N=64 |

Итого: **4 × 4 × 3 × 3 = 144 симуляции**. Для каждого типа и QoS общая offeredRps одинакова в single и трёх вариантах пула. В пуле на каждый из четырёх backend приходится четверть внешней нагрузки.

DirectBalanced обязателен: рост производительности при переходе с одного брокера на четыре нельзя приписывать только алгоритму назначения подключений. Сравнение RR и Least Connections при одинаковой карте должно показывать одинаковый модельный результат, если прочие условия совпали.

Короткая матрица предназначена для проверки всей цепочки и первичного анализа. Она не подтверждает стационарную точность p99 или точность реального балансировщика. Реальное время расчёта оценить по smoke и тяжёлой точке; заданный wall-time и ускорение не обещаются.

В v1 матрица выполняется последовательно. Параллельность независимых процессов можно исследовать отдельно после проверки памяти; она не должна менять параметры или состояние одного опыта.

## 8. Результаты и формулы

| Показатель | Определение |
| --- | --- |
| configuredOfferedRps | Заданная общая интенсивность внешней подачи |
| scheduledPublishes | Предусмотренное расписанием число публикаций; backpressure показывается отдельно |
| apiAttempts | Реально выполненные вызовы Publish в measurement |
| sendRejected | Вызовы Publish, сразу вернувшие отказ; это не все возможные протокольные ошибки |
| publisherPending | Число publishers с HasPendingPublish на границе фазы; это не все пакеты в пути |
| backendCompletedRps | Число завершений измерительной генерации backend / длительность measurement |
| uniqueGoodput | Уникальные измерительные ID, полученные ожидаемым receiver / длительность measurement |
| attemptDeliveryLoss | 1 − uniqueReceivedMeasurementIds / apiAttempts |
| backendPublishFailureRate | (rateRejected + publishFailed) / backendAttempted |
| backendDeliveryLossRate | 1 − backendDelivered / backendExpectedDeliveries |
| Publish latency | p50/p95/p99 существующей гистограммы завершений backend для QoS 1/2 |
| Receiver latency | Квантили от tick вызова отправки до первого получения ID ожидаемым receiver |

При нулевом знаменателе отчёт должен показывать неприменимость оценки, а не делать вывод об отсутствии потерь. Сохраняются сами числители и знаменатели. Завершения и получения до окончания measurement и во время drain показываются отдельно. Goodput, включающий drain, относится к измерительной когорте сообщений и не равен мгновенной скорости приёма только внутри окна.

Глобальные квантили вычисляются из объединённых гистограмм, а не усреднением p99 backend. QoS 0 ACK latency — notApplicable. CPU/RSS настоящего брокера и ресурсы реального proxy не моделируются; полную ресурсную оценку EST для такой модели не заявлять.

Пакет результата:

- `manifest.json`: настройки, версия приложения, commits, runtime, профили и их SHA-256/provenance, назначения и использованные профильные точки;
- точный снимок config и исходных файлов профилей;
- `assignments.csv`, `backend-metrics.csv`, `summary.json`;
- гистограммы завершений и получений, счётчики фаз и диагностические причины отказа;
- экспорт топологии;
- `report.md` с таблицами и ограничениями, графики SVG из CSV стандартным инструментарием Matplotlib;
- `sha256.json` для файлов пакета, кроме самого реестра.

Графики: распределение publishers и goodput по backend; single/directBalanced/RR/LC по completion RPS, unique goodput и задержкам. Таблицы и графики строятся из одного набора сохранённых чисел. Для v1 графики формирует небольшой Python-скрипт по выходным CSV; симулятор не зависит от Python при выполнении одной точки.

## 9. Проверки

### Алгоритмы и учёт

- [ ] RR даёт ожидаемую карту, разность числа подключений не больше одного.
- [ ] Least Connections учитывает pending reservations и детерминированно разрешает равенство.
- [ ] Backend клиента неизменен на всём обмене QoS 1/2.
- [ ] Служебные receivers не меняют решение политики назначения publishers.
- [ ] Для матрицы получаются 64 publishers на single и 16 на каждом backend пула.
- [ ] Для v4 отсутствующие N, payload или QoS отклоняются без интерполяции и замены соседней точкой.
- [ ] Подписчик backend B не получает публикации backend A без механизма связи брокеров.
- [ ] Для идеальной сети локальная уникальная доставка подтверждается при QoS 0/1/2.
- [ ] Прогрев не входит в измерительную когорту; её поздние доставки выделены в drain.
- [ ] Дубликат receiver-события не увеличивает unique goodput; неизвестный ID и неверный backend диагностируются.
- [ ] Агрегированные backend-счётчики равны суммам backend, глобальные квантили проверены по объединённой гистограмме.
- [ ] Тот же seed и те же входы дают одинаковые научные результаты; служебные ID и wall-time исключены из сравнения.
- [ ] DirectBalanced, RR и Least Connections с одинаковой картой не создают выдуманного выигрыша.

### Ошибки и совместимость

- [ ] Неверные входы, существующий output, непригодные профили и несовместимое происхождение обнаруживаются до нагрузки.
- [ ] Недостаточный timeout подключения/подписки/drain возвращает явный технический статус и сохраняет диагностику.
- [ ] Профили читаются из одного snapshot, хэш относится к использованным байтам.
- [ ] Существующие BrokerFidelity, MqttRelay, calibration и regression tests проходят после добавления проекта.
- [ ] Новое приложение не изменяет старые CLI, схемы конфигураций и опубликованные данные.

## 10. Этапы реализации и приёмки

1. Добавить один app-проект и ссылку на него из существующих integration-тестов. Зафиксировать настройки и контракт результатов.
2. Реализовать чистые политики назначения и их тесты.
3. Реализовать построение сети, фазы, нагрузку и ledger через существующие API.
4. Добавить writer, формулы, диагностику и воспроизводимый отчёт.
5. Выполнить существующие регрессионные проверки и **12 идеальных smoke-прогонов**: четыре режима × три QoS, seed 42.
6. Проверить ресурсы и выполнить 144 исследовательских запуска с сохранёнными профилями. При отказе показывать фактическое покрытие; незавершённую серию не объявлять полной.
7. Подготовить сравнение и ограничения. Не заявлять превосходство политики при совпавших назначениях или натурную точность LB без отдельного реального эталона.

Успешная приёмка v1 означает: новое расширение запускается, корректно назначает соединения, сохраняет однозначные метрики и повторяет научные результаты, а прежние возможности MqttY проходят регрессионные проверки. Расширение исследования на proxy, отказы, динамические сессии и Relay оформляется отдельной программой.
