# Метрики MqttBenchmark, BrokerFidelity и MqttRelay

Справочник для чтения натурных измерений и симуляций. Формулы соответствуют текущим экспортируемым observations и scientific summaries. Конкретные окна, версии и параметры всегда берутся из манифеста соответствующей серии.

## 1. Типы показателей

| Тип | Что описывает | Примеры | Единицы |
| --- | --- | --- | --- |
| Нагрузка | Что подаёт генератор | payload, publishers, offeredRps | байт, клиенты, публикации/с |
| Счётчики | События за окно наблюдения | attempted, completed, delivered | события |
| Производительность | Скорость завершения работы | attemptedRps, completedRps | публикации/с |
| Надёжность | Ошибки публикаций и недоставка | publishFailureRate, deliveryLossRate | доля 0–1 |
| Задержки | Время до определённого события | p50, p95, p99, RTT | мс |
| Ресурсы | Нагрузка на реальную машину | CPU, RSS | %, байт или MiB |
| Статистика | Разброс повторных запусков | mean, SD, CI95 | единицы исходного показателя |
| Качество модели | Отличие симуляции от наблюдения | RPS error, p99 error, loss difference | относительная ошибка или разность долей |
| Покрытие и целостность | Что выполнено и что сохранено | successful keys, failed attempts, seals, SHA-256 | количество, статус, хэш |

## 2. Нагрузка и идентификация точки

- `messageBytes` / `payloadBytes`: размер полезной нагрузки сообщения; MQTT/TCP/IP overhead сюда не входит.
- `qos`: 0 — без подтверждения публикации; 1 — PUBACK; 2 — завершение обмена PUBCOMP. QoS публикации и QoS подписки задаются отдельно.
- `publishers`: число публикующих клиентов натурного брокера. В сети важно читать конфигурацию: это может быть число клиентов **на брокер**.
- `repeat`: отдельное натурное измерение той же точки. `seed`: начальное состояние генератора случайных чисел симулятора. Несколько seeds не заменяют независимые натурные измерения.
- `offeredRps`: заданная внешняя интенсивность. Она не обязана совпадать с фактической attempted или completed интенсивностью, особенно при closed-loop ограничении числа незавершённых публикаций.
- `closedLoopPerPublisher`: не более одной незавершённой публикации QoS 1/2 на publisher. `openLoopRate`: попытки задаются по времени без такого ожидания; ограничения модели могут отклонять их.

В однородной сети текущей ночной серии внешний offeredRps равен `4 × attemptedRps` одиночного брокера. На каждый из четырёх узлов приходится четверть внешней нагрузки. Внутренние пересылки Relay создают дополнительные события, не входящие в этот внешний offeredRps.

## 3. Натурные счётчики и скорости

Обозначим A — `attemptedPublishes`, C — `completedPublishes`, F — `failedPublishes`, D — `completedIdsDelivered`, T — `actualMeasurementSeconds`.

| Метрика | Определение | Интерпретация |
| --- | --- | --- |
| attemptedPublishes | Число попыток публикации | Работа, предложенная MQTT-клиентом |
| completedPublishes | Успешные завершения вызова публикации | QoS 1/2: завершение подтверждаемого обмена; QoS 0 не имеет MQTT ACK |
| failedPublishes | Неуспешные публикации | Не равно числу сообщений, не полученных подписчиком |
| completedIdsDelivered | Уникальные ID успешных публикаций, полученные подписчиком | Проверка доставки отделена от подтверждения публикации |
| uniqueDeliveries | Уникальные полученные ID | Может иметь иной охват, чем completedIdsDelivered |
| duplicateDeliveries | Повторные получения ID | Не увеличивают число уникально доставленных сообщений |
| unexpectedDeliveries | Получения, не соответствующие ожидаемым ID | Диагностический счётчик |
| deliveredAfterFailedPublish | Сообщения, полученные несмотря на неуспешное завершение публикации | Показывает различие клиентского исхода и доставки |
| attemptedRps | A / T | Фактическая интенсивность попыток |
| completedRps | C / T | Фактическая интенсивность успешных завершений |
| publishFailureRate | F / A | Доля неуспешных публикаций |
| deliveryLossRate | 1 − D / C | Доля ID завершённых публикаций, не полученных до окончания наблюдения |

При нулевом знаменателе соответствующая реализация возвращает 0. Такой ноль сам по себе не доказывает надёжность: сначала проверьте наличие попыток и завершений.

`deliveryLossRate=0,2` означает 20% недоставки **за наблюдавшееся время**, а не 0,2%. Это не доказывает, что сообщения сбросил именно брокер: возможны очереди, получатель, TCP и ограничения наблюдения. Успешный PUBACK/PUBCOMP не является подтверждением получения прикладным подписчиком.

## 4. Задержки и RTT

| Метрика | Смысл |
| --- | --- |
| p50 | Медиана: примерно половина наблюдавшихся завершений не медленнее этого значения |
| p95 | 95-й процентиль времени завершения |
| p99 | 99-й процентиль; чувствителен к редким задержкам и размеру выборки |
| min / max | Наблюдавшиеся крайние значения; не доверительный интервал |
| RTT baseline | Время отдельного контрольного обмена туда-обратно; не эквивалент MQTT PUBACK/PUBCOMP latency |

Для QoS 1/2 publish latency измеряет время до завершения публикации, **не задержку до подписчика**. Для QoS 0 ACK latency — `notApplicable` / «неприменимо», а не ноль.

В натурной агрегированной таблице p99 — среднее p99 отдельных повторов. В эмпирическом профиле используется объединённая гистограмма; её p99 может отличаться от среднего p99 повторов. Это разные статистики. Нельзя подменять одну другой ради прохождения порога. Пример Aedes: p99 повторов 3,771 / 3,776 / 6,827 мс; среднее около 4,791 мс, а p99 объединённой выборки около 3,799 мс.

## 5. Окна времени и drain

- **Warmup**: прогрев перед измерением; не входит в номинальную длительность нагрузки measurement.
- **Measurement**: основное окно измерения нагрузки.
- **Drain**: ожидание завершения оставшихся операций и доставки после прекращения новых публикаций, с заданным таймаутом.
- **Cooldown / quiet period**: завершение и ожидание спокойного состояния между попытками.
- **Telemetry capture envelope**: полное окно сбора телеметрии, которое шире measurement. Reserve — запас захвата, а не добавочная длительность основной нагрузки.
- **Tick**: шаг модельного времени. Микросекунда модельного времени не равна микросекунде реального времени исполнения.

Benchmark делит на сохранённое `actualMeasurementSeconds`; simulator — на фиксированную длительность модельного measurement. В симуляторе завершения в drain могут входить в числитель при неизменном знаменателе. Поэтому сравнивать только RPS без правил окон недостаточно. Короткое модельное окно повышает относительный вклад границ и drain.

## 6. Счётчики симулятора и сети Relay

| Поле summary.simulated | Смысл |
| --- | --- |
| attempted | Попытки, зарегистрированные модельными брокерами |
| admitted | Попытки, принятые на обработку |
| completed | Завершённые модельные публикации |
| rateRejected | Отказы на допуске по ограничению интенсивности |
| publishFailed | Прочие модельные неуспешные публикации после допуска |
| expectedDeliveries | Ожидаемые модельные доставки |
| delivered | Доставки, учтённые моделью брокеров |
| deliveryDropped | Модельные сбросы доставки |
| completedRps | Сумма брокерных completed RPS |
| publishFailureRate | (rateRejected + publishFailed) / attempted |
| deliveryLossRate | 1 − delivered / expectedDeliveries |
| receivers | Счётчики конечных receiver-узлов из экспортированных counters |

В Relay агрегируются события нескольких брокеров, включая внутренние пересылки. `attempted` и `completed` сети нельзя объявлять числом уникальных внешних сообщений. `delivered` брокеров и сумма `receivers` также имеют разную семантику.

Receiver counters могут включать поступления в drain и сообщения, начатые во время warmup и пересёкшие границу сброса. Они подтверждают доставку в модельные receiver-узлы. Без сквозного ID-учёта и разделения источников не доказывают уникальную межброкерную доставку каждого внешнего сообщения. Для физических удалённых MQTT-получателей требуется отдельный натурный опыт.

## 7. CPU, память и guard

| Метрика | Область измерения | Ограничение интерпретации |
| --- | --- | --- |
| captureCpuMeanPercent | Средний CPU процесса брокера за полный capture envelope | Не среднее только measurement |
| captureRssMaxBytes | Максимальный RSS процесса брокера за capture | RSS — резидентная память, не весь виртуальный адресный объём |
| CPU guard | Общесистемный CPU по пересекающим measurement интервалам | Guard 99% не означает, что генератор гарантированно не ограничивает RPS |
| maximumIntervalSeconds | Предельный допустимый разрыв между замерами sampler | Превышение может сделать попытку технически непригодной |
| MemoryCurrent / MemoryMax | Память и лимит systemd/cgroup | Иной охват, чем RSS одного брокера |

MiB = 2²⁰ байт, GiB = 2³⁰ байт. Одно закреплённое логическое CPU не является эксклюзивным физическим ядром. CPU/RSS — натурные свойства стенда; текущий двойник не моделирует их.

## 8. Повторы, среднее и доверительный интервал

Для трёх независимых повторов: `mean = Σx / 3`; `SD = sqrt(Σ(x − mean)² / 2)`; **CI95 = mean ± 4,30265273 × SD / √3**, Student-t, df=2.

CI описывает неопределённость среднего при предпосылках метода. Он не охватывает 95% отдельных сообщений и не является диапазоном p95/p99. Три повтора дают ограниченную статистическую мощность; пересечение CI не доказывает эквивалентность. Доверительные интервалы долей могут выходить за [0;1], если применена эта необрезанная формула. Seeds модели оценивают модельную вариативность, не весь разброс реального стенда.

## 9. Критерии точности BrokerFidelity

| Критерий | Ошибка | Прежний неизменённый порог |
| --- | --- | --- |
| rps | abs(simulated − reference) / abs(reference) | ≤ 0,15, то есть 15% |
| latencyP99Ms | abs(simulated − reference) / abs(reference) | ≤ 0,20, то есть 20%; QoS 1/2 |
| publishFailureRate | abs(simulated − reference) | ≤ 0,05, то есть 5 процентных пунктов |
| deliveryLossRate | abs(simulated − reference) | ≤ 0,05, то есть 5 процентных пунктов |

Для нулевого эталона относительная ошибка обрабатывается кодом отдельно; результат и статус берутся из сохранённого acceptanceCriteria. Не делите вручную на ноль.

`passed` — критерий применим и выполнен. `failed` — применим и нарушен. `notApplicable` — сравнение неприменимо; это **не прохождение проверки**. У Relay все эти сравнения могут быть notApplicable: натурная точность сети данной кампанией не установлена.

Fidelity — воспроизведение калибровочных наблюдений. Holdout — сравнение с новой натурной серией при неизменном профиле. Первая проверка не заменяет вторую. Набор для разработки модели нельзя объявлять слепой независимой проверкой.

## 10. Покрытие, ошибки и доказательства

Запись `✅72/72 · ❌1 · ⚠8` читается так: 72 успешных ключа из 72 запланированных; одна дополнительная технически неуспешная попытка; восемь завершённых сценариев нарушили один или несколько научных критериев. Это не 63 успешных запуска. Несколько критериев могут нарушаться в одном сценарии.

Технические причины — например, отсутствие покрытия телеметрии, guard, запуск CLI или таймаут. Они сохраняются с исходными evidence и могут требовать retry. Провал fidelity — содержательный результат, который не устраняется исключением сценария.

SHA-256 и seals подтверждают целостность конкретных файлов. `verified=true` в archive-verification означает выполненную проверку восстановления и агрегации в описанном там объёме. Восстановленный aggregate может иметь другой файловый SHA из-за другой inputSha256-карты, сохраняя те же scientific points и campaign identity. Для научной проверяемости нужны raw, точные входы, версии, команды и повторный расчёт; одного хэша недостаточно.
