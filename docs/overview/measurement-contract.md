# Контракт измерений и независимой проверки

Этот документ фиксирует смысл показателей, которые используются в двух статьях и диссертации. Он относится к сохранённой натурной кампании четырёх брокеров и объясняет, что именно можно проверить по её журналам. Точные версии кода, входов и результатов закрепляются хэшами в наборе доказательств.

## 1. События и состав данных

Натурный опыт запускает MqttBenchmark. Он создаёт MQTT-клиентов, подаёт нагрузку, получает сообщения подписчиком и сохраняет события. MqttY исполняет отдельную модель; натурные сообщения через него не проходят. Проверяющий Python-код читает архивы и независимо пересчитывает результат, не вызывая функции агрегирования MqttBenchmark или генератора отчётов.

| Источник | Что подтверждает |
| --- | --- |
| `publishes.ndjson`, событие `attempt` | Генератор зарегистрировал попытку вызова Publish API с ID, publisher, sequence, размером и временем |
| `publishes.ndjson`, `completed` | Вызов Publish завершился успешно; для QoS 1/2 сохранена длительность вызова |
| `publishes.ndjson`, `failed` | Вызов закончился ошибкой; сохранены причина и время |
| `deliveries.ndjson` | Обработчик subscriber получил ID и размер сообщения; есть время получения |
| `result.json` | Записанная сводка, параметры точки, статус попытки и идентичность кампании |
| `sha256.json` | Ожидаемые хэши всех остальных файлов архива |
| Маркеры измерения и частота timestamp | Монотонная длительность измерения, независимо от записанного RPS |
| Телеметрия, guard и provenance | Состояние измерительной установки и основания принятия попытки |

Попытка API не означает, что PUBLISH был передан в сеть или принят брокером. После отключения клиента возможны быстрые локальные ошибки. Успешное завершение API тоже не означает получение сообщения subscriber.

Измерительные ID независимо восстанавливаются из JSON-массива `[campaignId, runId, publisher, sequence]`: SHA-256, первые 16 байт. Это позволяет обнаружить чужой запуск, ID прогрева, повторную попытку и нарушение последовательности. Идентичность `runId` включает номер попытки. Проверка совместимости сериализации относится к используемым в кампании ASCII-идентификаторам.

Журнал хранит ID и размер, но не всё содержимое payload. Поэтому по нему нельзя заново проверить неизменность остальных байтов тела сообщения. Эта граница доказательств сохраняется в выводах.

## 2. Счётчики и формулы

Обозначения для одного натурного запуска:

- **A** — число уникальных зарегистрированных попыток;
- **C** — число ID с успешным завершением;
- **F** — число ID с ошибкой завершения;
- **D** — число уникальных известных ID, полученных subscriber независимо от исхода API;
- **Dс** — число полученных ID из множества C;
- **Dф** — число полученных ID из множества F;
- **T** — фактическая монотонная длительность измерения.

| Поле | Определение | Единица |
| --- | --- | --- |
| `attemptedPublishes` | A | Публикации |
| `completedPublishes` | C | Публикации |
| `failedPublishes` | F | Публикации |
| `uniqueDeliveries` | D | Уникальные известные ID |
| `completedIdsDelivered` | Dс | Уникальные ID |
| `deliveredAfterFailedPublish` | Dф | Уникальные ID; название не устанавливает порядок получения и ошибки |
| `duplicateDeliveries` | Все получения каждого ID после первого, включая неожиданные ID | События |
| `unexpectedDeliveries` | Все получения ID, отсутствующих среди попыток | События, не число уникальных чужих ID |
| `attemptedRps` | A / T | Публикации/с |
| `completedRps` | C / T | Публикации/с |
| `publishFailureRate` | F / A | Доля |
| `deliveryLossRate` | 1 − Dс / C | Доля среди успешных завершений |
| Полнота относительно попыток | D / A | Доля; используется в доставочном слагаемом EST |

Для принятого успешного запуска должны выполняться `A=C+F`, отсутствие двух исходов одного ID и `D=Dс+Dф`. Неурегулированные ID показываются отдельно. Дубликаты и неожиданные получения пересчитываются, даже если их число в записанной сводке равно нулю.

При A=0 или C=0 исходная программа сохраняет соответствующую долю равной нулю. Это вычислительное соглашение, а не доказательство отсутствия отказов или потерь. В содержательном сравнении указывается нулевой знаменатель; без положительного T скорость не определена.

Недоставка до конца наблюдения сама по себе не устанавливает причину. По одному агрегату нельзя различить задержку, очередь, перегрузку получателя, локальную ошибку и сброс внутри брокера.

## 3. Задержки и квантили

**Задержка завершения публикации** измеряется вокруг вызова Publish API. Для QoS 1/2 в исследуемом клиенте это ожидание соответствующего MQTT-обмена, с включением клиентских накладных расходов. Это не чистая задержка обработки внутри брокера и не время до subscriber.

Для QoS 0 публикационного ACK нет: `publishLatencyMs=null`, `latencyStatus=notApplicable`. Нулевую задержку вместо неприменимости подставлять нельзя. Для QoS 1/2 без успешных завершений статус — `unobserved`, а не «задержка равна нулю».

Из конечных неотрицательных задержек успешных завершений строится упорядоченный ряд. Для вероятности p используется ближайший верхний ранг `ceil(p×n)`, с ограничением индексом первого/последнего значения. Проверяются min, p50, p75, p95, p99 и max. Среднее p99 трёх запусков не называется p99 объединённого потока.

**Задержка первого получения** дополнительно восстанавливается как время первого известного ID в журнале subscriber минус время его зарегистрированной попытки. Обе отметки относятся к одним workload-часам. Начало интервала расположено до допуска в транспорт, поэтому показатель подписывается «от зарегистрированной API-попытки», а не «от отправки пакета». В расчёт входят только полученные известные ID; рядом обязательно показывается полнота доставки. Малый p99 среди немногих получений не означает хорошую доставку всего потока.

**RTT baseline** сохраняется по отдельным preflight-обменам. Это исходное наблюдение транспорта/клиента, а не тот же показатель, что публикационная задержка или путь до прикладного receiver. Заново выполненным измерением RTT чтение сохранённого протокола не является.

## 4. Время, прогрев и drain

В натурном коде измерительный PublishWindow ожидает завершения задач publishers. Поэтому фактическое T может включать ожидание последних исходов за номинальным дедлайном. Оно независимо сверяется с разностью монотонных tick начала и конца, делённой на сохранённую частоту timestamp. Календарные UTC-отметки используются как отдельная проверка, не заменяя монотонный знаменатель.

Прогрев публикует в другую тему и использует другое пространство ID. Журналы измерительных попыток проверяются по ожидаемому хэшу каждого ID. Получения и исходы нельзя исключать только по визуальной близости времени к номинальному warmup.

Все исходные публикации урегулированы до перехода в drain в исследуемом успешном коде. Drain позволяет subscriber получить ещё не доставленные ID этой когорты. Итоговые счётчики включают такие доставки, а RPS делится на фактическое T. Это следует отличать от симуляции, где завершения во время drain могут относиться к когорте фиксированного окна подачи нагрузки.

**Точная граница получения measurement/drain в workload-секундах не сохранена.** У абсолютных tick и времён NDJSON нет записанного общего начала отсчёта. Для успешного кода можно восстановить консервативный интервал:

`время последнего исхода ≤ конец измерения ≤ время первой попытки + T`.

Получения до нижней границы заведомо предшествуют концу измерения; после верхней — заведомо следуют за ним. Получения внутри интервала отмечаются как неопределённые у границы. Они учитываются в полной доставке, но им не присваивается выдуманная точная фаза. Если предпосылки исполнения или временной порядок нарушены, это отдельное расхождение, а не основание поправить границы вручную.

## 5. Повторы, сравнение с моделью и EST

Натурная точка содержит три самостоятельных повтора. Для средних приводятся стандартное отклонение и Student-t CI95; при n=3 используются две степени свободы. Интервал характеризует разброс доступных повторов. Интервал среднего p99 не является автоматически интервалом самого квантиля объединённых данных.

Fidelity сравнивает модель с калибровочными наблюдениями. Holdout использует отдельные натурные наблюдения при неизменённом профиле. Если алгоритм или профиль подбирается по этому контролю, его нельзя затем объявлять новым независимым доказательством. Текущий offered RPS для контрольной симуляции берётся из attempted RPS контрольной точки; это условная проверка при известной интенсивности, не слепое предсказание нагрузки.

Критерии фиксированы: RPS ≤15% относительной ошибки, p99 QoS 1/2 ≤20%, абсолютная разность publish failure и delivery loss ≤0,05. Неприменимые показатели отделяются от прошедших. Допуски сами по себе не являются статистическим тестом эквивалентности.

Для EST веса четырёх слагаемых равны 0,25:

`EST = 0,25×R/max(R_B) + 0,25×(1−Ccpu) + 0,25×(1−L/max(L_B)) + 0,25×(1−Fest)`.

Здесь R — средний completed RPS; Ccpu — средняя доля CPU процесса относительно одного закреплённого логического CPU; L — среднее публикационное p99; `1−Fest` — среднее D/A. Максимумы R и L считаются по четырём брокерам в одной нагрузочной точке. Сначала рассчитываются показатели повторов, затем средние; знаменатели разных долей не подменяются.

Строгая формула применяется к QoS 1/2. Для QoS 0 адаптация EST* исключает отсутствующее слагаемое L и перенормирует остальные веса. Нулевые максимумы обрабатываются явно: скоростное слагаемое при max(R)=0 равно 0, задержочное при max(L)=0 и наблюдавшихся нулевых задержках равно 1. Отсутствующие наблюдения не заменяются нулевыми задержками.

CPU и RSS — натурные ресурсные наблюдения, а не моделируемые свойства двойника. Значение EST от 0 до 1 не является вероятностью истинности или точностью симуляции. Рейтинг зависит от выбранных весов, набора брокеров и нагрузок; требования к минимальной доставке проверяются отдельно.

## 6. Проверяемость и сохранение результата

Для каждого архива фиксируются ожидаемый/фактический SHA-256, число проверенных внутренних seals, соответствие опубликованному запуску, счётчики, все доступные ACK-квантили, ошибки, временные проверки и ограничения. Неудачные попытки сохраняются отдельно от 576 выбранных успешных измерений.

Результат проверки считается согласованным, если совпали пересчитанные и записанные показатели, нет нарушений идентичности и отсутствуют неурегулированные исходы успешного запуска. Совпадение не доказывает отсутствие систематической ошибки самого стенда: clock evidence, версия кода, guard и условия опыта остаются частью научной оценки.

При расхождении исходный архив и старый отчёт сохраняются. Указывается затронутый показатель, доступное доказательство и допустимость использования данных. Изменение определения метрики или кода создаёт новую версию методики; пороги не подбираются для улучшения доли прошедших запусков.

Исходники проверки: `tools/dissertation/native_audit.py` и `run_native_audit.py`. При запуске сохраняются копии входов и кода. Возобновление допускается только при совпадении их хэшей; повтор после технической ошибки получает новый файл попытки проверки. Распаковка архивов и очистка исходных данных не выполняются.
