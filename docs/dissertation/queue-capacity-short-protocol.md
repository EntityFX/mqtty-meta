# Короткая пара очередей после технического отказа

Используются writing-plans, TDD и verification-before-completion. Это новая диагностическая программа, не повтор с продлением старого срока. Предыдущие попытки 1024/4096 сохраняются: baseline завершился, вариант 4096 достиг таймаута.

## Входы, фиксируемые до запуска

Источник — прежний `matrix.star.federation.q2.r1000.w10.s42.json`. Для обоих новых запусков одинаково задаются прогрев **0,25 с**, подача **2 с**, drain **до 10 с**. Сохраняются четыре брокера, 64 publishers, четыре subscribers, 16 байт, QoS 2, 1000 сообщ./с, seed 42, tick 0,1 мс, кэш 100000 и лимит переходов 4. Профиль не подключён. Между двумя вариантами меняется только `queueCapacity`: **1024 → 4096**. Модельный runtime и in-flight не меняются.

Окно сокращено для уменьшения вычислительной работы после подтверждённого таймаута, не для выбора лучшей точности или доставки. Завершение за заданное время не гарантируется. С прежней десятисекундной нагрузкой новую пару нельзя объединять как повтор того же условия.

## План и пределы

1. Тесты допуска отвергают второй изменяемый фактор и неверные окна. Отдельно проверяется счётчик законченных процессов: один законченный процесс должен отображаться сразу, без ожидания второго.
2. До запуска проверить отсутствие работающих исследовательских задач, запас RAM/диска и все 281 файла замороженного manifest. Скопировать runtime в новый каталог; закрепить SHA конфигов, бинарных файлов, dotnet host, протокола и оркестратора.
3. Запустить ровно два процесса параллельно: каждому до **240 с** и **2 ГиБ RSS**, службе до **600 с**, **6 ГиБ RAM**, **200% CPU**. Общий срок записывается один раз; повторный вход в тот же каталог запрещён. Резерв завершения/проверки — 120 с. Автоматического retry нет.
4. Сохранять отдельно команды, elapsed/RSS/PID каждого процесса и исход. Этот runtime не выдаёт промежуточные модельные фазы/тики; их нельзя выдумывать по elapsed. По окончании сохранить реальные фазы и пересчитать ID, payload, доставки, пересылки и гистограммы.
5. Повторно проверить исходный snapshot и новые закреплённые файлы. Сохранять все попытки, включая timeout; незавершённый вариант не получает нулевых потерь или задержки.

## Правило интерпретации

Если оба результата приняты, сравнить полноту, число получений и p99, queueDrops, доставки всем и drain. Если у 1024 нет переполнений, пара считается **неинформативной для перегрузки**, даже при полном совпадении: нагрузку автоматически не увеличивать. Иначе различия характеризуют только изменение размера очереди в этом коротком эпизоде. Один seed не даёт статистического обобщения и не выравнивает организацию выходов MqttRelay и федерации.

После запуска один раз подтвердить службу/PID и progress, обновить Progress.md, опубликовать проверенные изменения и остановить агента для ожидания. Новых таймеров и циклических опросов нет. Результаты будут приняты отдельным продолжением.
