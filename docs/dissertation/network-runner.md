# Запуск и возобновление сетевой программы

Оркестратор `tools/dissertation/run_network_study.py` управляет отдельными процессами Federation.App. Он не меняет MQTT-модель, профили или существующие кампании. Основной целевой запуск — Linux; проверки разработки выполнены локально на Windows.

| Часть | Что делает |
| --- | --- |
| `prepare_network_study.py` | Создаёт программу и конфигурации |
| Команда `stage` | Проверяет чистоту Git, копирует входы, код и runtime в новый каталог, сохраняет SHA и версии |
| Команда `run` | Последовательно исполняет один выбранный этап, контролирует ресурсы, проверяет журналы и сохраняет прогресс |
| Federation.App / ядро MqttY | Выполняет модель и сохраняет публикации, получения, пересылки, гистограммы и топологии |
| `network_study_verification.py` | Независимо пересчитывает журналы нагруженного опыта |
| Оператор и автор | Проверяют завершение предыдущей серии, оценивают pilots и достаточность программы |

## Подготовка на Linux

Нужны Python 3.11+, .NET runtime 6, Git и собранный Federation.App. Исходники мета-репозитория и MqttY должны быть закоммичены и чисты. Полные данные размещаются на отдельном смонтированном диске, не в корне системной файловой системы.

Пример команд Bash; переменные обозначают реальные пути выбранной машины:

```bash
repository=/path/to/mqtty-meta
evidence_mount=/path/to/mounted-disk
network_study="$evidence_mount/mqtty-evidence/network-long-v1"
runtime_dir="$repository/mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.Federation.App/bin/Release/net6.0"

dotnet build "$repository/mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.Federation.App" -c Release
python3 "$repository/tools/dissertation/run_network_study.py" stage \
  --source-root "$repository" \
  --program "$repository/reports/audits/dissertation/network-study-v1" \
  --runtime "$runtime_dir" --mount-root "$evidence_mount" --output "$network_study" \
  --after-unit mqtty-sensitivity-v1.service
```

`--after-unit` задаёт проверку изоляции от указанной пользовательской службы; флаг можно повторить. Служба должна существовать, быть неактивной и завершиться успешно. На другом стенде указываются его службы. Если прежняя transient-служба уже выгружена из systemd, сначала проверьте её итоговые результаты, затем создайте новый execution snapshot без этой зависимости. Файл manifest вручную не исправляется.

Копируются только входы и зависимости, а не прежние результаты. Сохраняются `dotnet --info`, SHA исполняемого host, DLL, конфигураций, профиля и проверяющего кода. Установленный shared runtime .NET остаётся внешней зависимостью: его версию нельзя менять в ходе серии. Незапланированные файлы внутри снимка, подмена входов или другой загруженный код вызывают отказ.

## Pilots и отдельный переход к матрице

```bash
systemd-run --user --unit mqtty-network-pilot-v1 \
  --property=MemoryMax=4G --property=MemorySwapMax=0 \
  --property=CPUWeight=10 --property=KillMode=control-group \
  --property=RuntimeMaxSec=12h \
  python3 "$network_study/tools/dissertation/run_network_study.py" run \
  --study "$network_study" --phase pilot
```

Выполняются только 30 pilots, по одному процессу. Следующий этап сам не стартует. Длительность 12 часов в примере — технический предел службы, не прогноз стоимости.

После pilots требуется запись оценки в отдельном JSON:

```json
{
  "decision": "accept",
  "executionManifestSha256": "<SHA execution-manifest.json>",
  "pilotResultsSha256": "<SHA results-pilot.json>",
  "reviewer": "<кто проверил pilots>",
  "reason": "<вывод о фазах, наблюдениях, памяти, месте и времени; ограничения>"
}
```

Так фиксируется основание выбора программы, а не достижение порогов точности. Недоставку нельзя убрать из данных ради перехода к матрице. Если длительности недостаточны, создаётся новая версия программы с сохранением старых pilots. Недостаток событий завершения ACK во времени остаётся ограничением текущего приложения: оркестратор не восстанавливает отсутствующие события из итогового p99.

```bash
python3 "$network_study/tools/dissertation/run_network_study.py" run --study "$network_study" --phase matrix --decision /path/to/pilot-assessment.json
python3 "$network_study/tools/dissertation/run_network_study.py" run --study "$network_study" --phase replay
```

Для этих длительных этапов также применяется отдельная systemd-служба с ограничением всей группы процессов. Необязательная диагностика запускается только явным `--phase diagnostic --decision ...`; она не добавляется к идеальной матрице автоматически.

## Ограничения ресурсов и доказательства

- По умолчанию: 30 минут и 3 ГиБ наблюдаемого RSS на дочерний процесс, резерв диска 10 ГиБ, общий бюджет каталога 40 ГиБ. Значения фиксируются при `stage` соответствующими параметрами CLI.
- RSS дочернего процесса проверяется раз в секунду; короткий пик между проверками может быть пропущен. Поэтому для Linux нужен также жёсткий `MemoryMax` всей systemd-группы. Пик RSS управляющего Python-процесса фиксируется отдельно, как накопленный максимум текущего запуска, включая проверку журналов.
- При потере mount, нехватке места, превышении бюджета, timeout или исключении дочерний процесс останавливается; новые задачи не начинаются. Управляющий процесс не пишет новые receipts на исчезнувшую точку монтирования: причина остаётся в stderr/journal до восстановления диска.
- Полнота и задержки пересчитываются по исходным ID и парам доставки. Проверяются payload, конфиг, профиль, GraphML, источники и получатели. Сохранённые summary не принимаются без пересчёта.
- В нагруженном Relay отсутствие части экспортов не приравнивается автоматически к технической ошибке. Проверяются источник, адресат и отсутствие повторного экспорта; полная формула стоимости применяется при выполнении условий идеального опыта без потерь. Исторический верификатор старой серии не изменён.
- Повторы сравниваются побайтно по summary, гистограммам, публикациям, получениям, пересылкам и транзитным данным при их наличии. Время ОС, PID и RSS не включаются в доказательство детерминизма.

После этапа доступны `results-<phase>.json`, `summary-<phase>.csv`, `report-<phase>.md`, журналы каждой попытки и индивидуальные отчёты/диаграммы приложения. При отказе сохраняется `partial-<phase>.json` с причиной и доступными результатами. Полные данные и архивы в Git не добавляются.

В `progress.json` поле `counts` показывает завершения, неустранённые ошибки и предупреждения отдельно для каждого этапа; `attempts` — общее число попыток и накопленные отказы. Успешный retry устраняет текущую ошибку, но не обнуляет историю отказов.

## Resume, отказ и аварийное завершение

```bash
python3 "$network_study/tools/dissertation/run_network_study.py" run --study "$network_study" --phase pilot --resume
```

Resume перепроверяет seals, первичные журналы и их связь со снимком. Завершённые опыты повторно не запускаются. Потерянный индекс восстанавливается из уже проверяемого durable receipt. Повреждённые данные не пересоздаются незаметно.

Технический отказ не вызывает автоматический retry. После выяснения причины создаётся новая попытка:

```bash
python3 "$network_study/tools/dissertation/run_network_study.py" run --study "$network_study" --phase pilot --resume --retry-job '<ID>' --retry-reason '<проверенная причина и устранение>'
```

Если управляющий процесс погиб без конечного receipt, сначала проверьте systemd/journal и зарегистрируйте прерывание. Команда проверяет `/proc`, чтобы не повторить ещё работающий процесс:

```bash
python3 "$network_study/tools/dissertation/run_network_study.py" recover-interruption --study "$network_study" --job '<ID>' --reason '<подтверждённая причина завершения>'
```

Она сохраняет отсутствие известного exit code, хэши доступных файлов и причину. Симуляция при этом не запускается; затем применяется явный retry. Все старые попытки остаются. Если модель была принудительно убита до записи своих массивов из памяти, отсутствующие события не восстанавливаются: сохраняются только действительно доступные файлы и журналы.

После старта долгого этапа подтвердите службу/PID и progress, обновите общий журнал и завершите работу агента до ручного продолжения. Ошибку до создания progress ищите в journal: старый `completed` от другого этапа не доказывает успех нового запуска.

## Проверки разработки и Linux-preflight

Пройдены 68 тестов инструментов, включая 14 тестов оркестратора. На настоящем MqttY CLI выполнены 15 коротких локальных симуляций: 9 проверок трёх режимов и QoS 0/1/2, 3 опорных опыта и 3 точных повтора. Resume не добавил попыток. В Windows-тесте имитировался только признак mount; Git, свободное место, runtime и проверка журналов были реальными.

Это не покрытие научной матрицы. Дополнительно пройден Linux-preflight из 15 реальных CLI-опытов с настоящим mount и настроенным MemoryMax=3 ГиБ: три повтора совпали, resume не добавил попыток, пик около 220 МиБ. Исчерпание cgroup не вызывалось. Шаг 22 принят технически; для 21 остаются 30 содержательных pilots, оценка достаточности фаз и бюджета. Данные 75 выбранных научных JSON Windows/Linux совпали после нормализации CRLF/LF; исходные byte SHA различаются и сохранены.
