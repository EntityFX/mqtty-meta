Это техническая подготовка, а не уже полученное согласование автора или руководителя. Здесь различаются четыре пути: натурная кампания MqttBenchmark v3; одиночная модель с журналом ID; прежние общие счётчики MqttRelay; новая сетевая программа `FederationRunner` для single/Relay/federation. Привязка к версиям, SHA и таблица расхождений находятся в [квитанции сверки](../../reports/audits/dissertation/metrics-contract-20261030/README.md).

## 1. События, ID и исходы публикации

Попытка публикации — зарегистрированный вызов клиентского Publish API. Она не доказывает отправку PUBLISH в сеть или приём брокером. Быстрые локальные ошибки после разрыва соединения могут увеличить число попыток без увеличения полезной работы брокера. Успешный исход вызова и получение сообщения подписчиком — два разных события.

Для выбранной когорты попыток используются обозначения:

| Обозначение | Смысл |
| --- | --- |
| A | Число попыток с уникальными ID, попавших в заданное окно подачи |
| C | Число этих ID с успешным исходом к концу наблюдения |
| F | Число этих ID с ошибкой к концу наблюдения |
| P | Число ID без исхода к концу наблюдения: `A−C−F` |
| D_id | Число полученных известных ID выбранной когорты независимо от исхода вызова |
| Dс | Число полученных ID из множества успешных C |
| Dф | Число полученных ID из множества ошибочных F |
| T | Длительность явно названного окна в секундах |

`A=C+F+P` относится к одному набору ID и одному горизонту наблюдения. Равенство `D_id=Dс+Dф` допустимо только при P=0. Получение ID до регистрации успешного исхода также засчитывается в Dс, если исход успел появиться до горизонта. Состояние pending не следует автоматически превращать в ошибку или недоставку.

В Benchmark этим величинам соответствуют `attemptedPublishes`, `completedPublishes`, `failedPublishes`, `uniqueDeliveries`, `completedIdsDelivered`, `deliveredAfterFailedPublish`. `DeliveryLedger.Snapshot` требует урегулированных исходов; отдельного поля pending у этой сводки нет. Поле `deliveredAfterFailedPublish` означает принадлежность полученного ID к ошибочным исходам, а не доказанный порядок «ошибка, затем получение».[B1], [B2]

В одиночной проверке статьи 1 пересчёт выполняется по событиям `attempt/completed/failed` и ID. Новый Web `NativeControlCohort` также выделяет A, C, F, P и Dс, а не берёт доставку из общих брокерных счётчиков.[A1], [W1]

Общие модельные поля `attempted/admitted/completed/rateRejected/publishFailed` имеют иной уровень учёта: попытки и допуски на брокере. QoS 0 считается завершённым при допуске; QoS 1/2 — при завершении отслеживаемого обмена с отправителем. Ошибка общего счётчика равна `(rateRejected+publishFailed)/attempted`. Остаток в балансе брокера нельзя без сверки журналов объявлять P клиентской когорты. В сетевой сумме могут находиться как исходные публикации, так и внутренние пересылки.[M1], [M2]

## 2. Окна времени и скорости

Для когорты задаются начало подачи `b`, конец подачи `e` и конец наблюдения `h`. Попытки выбираются по `b ≤ t_attempt < e`; исходы и получения учитываются до h включительно. `T_submit=e−b`. При наличии общего монотонного начала отсчёта это проверяется по журналу фаз. Для принятой серии статьи 1 установлены прогрев 1 с, подача 4 с и последующее наблюдение 5 с; значения по умолчанию в новом Web не заменяют эти исторические настройки.[A1], [A2]

| Подпись величины | Формула и окно | Где встречается |
| --- | --- | --- |
| Попытки/с | `A/T` | Только с указанием используемого T |
| Завершения в окне/с | `C_window/T_submit`, исход строго до e | Статья 1: `completedRpsInWindow` |
| Завершения когорты на секунду подачи | `C_h/T_submit`, исход до h, включая drain | Статья 1: `completedCohortPerSubmissionSecond`; Web: `metrics.rps` |
| Натурные завершения/с по фактическому времени | `C/T_actual` | Benchmark: `completedRps`; T_actual включает ожидание исходов последних запущенных вызовов |
| Модельные завершения/с | Учтённые брокером завершения, включая drain, / фиксированное measurement | `MqttRelayExperimentRunner`: `completedRps`; сеть: `sourceCompletedRps` только по исходным отправителям |
| Скорость получения уникальных пар | `D_pair/T_submit` | Новая сеть: `uniqueGoodput`, включая первые получения во время drain |

Длительность drain не прибавляется к знаменателю опубликованного cohort RPS или сетевого goodput. Это скорость результата когорты относительно времени подачи, а не число событий получения за секунду всего наблюдения. В статье 1 отдельно сохранены `completedInWindow`, `completedDuringDrain` и `firstDeliveriesDuringDrain`.[A1], [N1]

Benchmark после дедлайна ждёт исходов уже запущенных вызовов. Его обычный `actualMeasurementSeconds` поэтому может быть больше номинального measurement. Новый когортный пересчёт использует границы из `phases`, даже если исходный `MeasurementSummary` того же запуска использует фактическое время. Нельзя сравнивать эти два `C/T` как одинаковые показатели без подписи окна.[B3], [A1]

У более ранней натурной кампании точная граница measurement/drain не сохранена в общей системе времени NDJSON. Существующий [контракт прежней кампании](../overview/measurement-contract.md) описывает лишь консервативный интервал границы. Это ограничение не переносится на новую серию статьи 1 с `sharedMonotonic`, и наличие новых фаз не исправляет задним числом старые журналы.

Offered RPS — заданная интенсивность внешней нагрузки, а не A/T, C/T или goodput. `closedLoopPerPublisher` ждёт предыдущий исход QoS 1/2; `openLoopRate` планирует попытки по интенсивности. В новой сетевой программе `scheduledPublishes` — запланированные слоты, `apiAttempts` — фактические исходные вызовы, `backpressureUnsent=scheduledPublishes−apiAttempts`. Неподанные слоты не входят в A и не считаются неуспешными API-вызовами.[N2]

## 3. Доставка: два разных знаменателя

Для одного наблюдаемого subscriber когортная недоставка успешных публикаций равна `L_success=1−Dс/C`. Числитель полноты Dс состоит только из полученных ID с успешным исходом. `D_id/A` отвечает другому вопросу: какая доля всех попыток дала известное получение, в том числе при ошибке API. Именно этот показатель используется в доставочном слагаемом EST прежней натурной серии.[B1], [E1]

При нескольких subscribers одной публикации соответствуют несколько ожидаемых пар «ID, получатель». Обозначим их число E, а число уникальных реально полученных ожидаемых пар — D_pair. Тогда `L_pairs=1−D_pair/E`. Нужно назвать когорту, из которой построено E: все попытки либо только успешные завершения. Эти варианты не эквивалентны.

В принятой основной сети E построено **по исходным API-попыткам**, независимо от завершения: `expectedDeliveries=apiAttempts×число ожидаемых receivers`. `uniqueDeliveries` здесь означает D_pair, а не число разных сообщений. Один ID у трёх receivers даёт три пары. `fullyDeliveredPublications` считает ID, полученные всеми ожидаемыми receivers. Поле `deliveryLoss=1−D_pair/E` нельзя подменять `1−Dс/C`.[N1], [N3]

Пример для одного subscriber: A=100, C=80, F=20, P=0, Dс=60, Dф=10. Недоставка среди успешных равна 25%, а полнота относительно попыток — 70%. Пример для сети: A=100, три ожидаемых receiver, E=300, D_pair=210. Полнота пар равна 70%, недоставка — 30%. Число полностью доставленных всем трём ID по одному D_pair восстановить нельзя. Примеры поясняют определения, не являются экспериментальными результатами.

Прежний `MqttRelayExperimentRunner` использует другую пару полей: `expectedDeliveries` и `delivered` брокерного fanout, без сквозного объединения по исходному ID и конечному receiver. Это полезный внутренний показатель, но не D_pair новой сетевой программы. Сумма всех брокерных RPS, доставок или ожиданий не равна числу уникальных внешних сообщений.[M1], [M2]

В этом словаре goodput предлагается всегда подписывать с объектом счёта и окном. Для одиночного subscriber можно отдельно вычислять `Dс/T_submit` или `D_id/T_submit`, указывая выбор; текущий Benchmark не публикует эти величины отдельным полем goodput. В сети уже реализован `uniqueGoodput=D_pair/T_submit`: единица — уникальные пары/с, а не уникальные сообщения/с и не байты/с. Скорость полностью доставленных всем receivers публикаций потребовала бы отдельной подписи и расчёта; это не переименование существующего поля.

## 4. Нулевые знаменатели и неполные наблюдения

| Путь | Что фактически записывает код |
| --- | --- |
| Benchmark v3 | При A=0 `publishFailureRate=0`; при C=0 `deliveryLossRate=0`; T_actual должен быть положительным |
| Общие счётчики Relay | При attempted=0 или expected=0 соответствующая доля равна 0; нулевое окно нормализуется в RPS=0 |
| Пересчёт статьи 1 и Web cohort | При A=0 failure=null; при C=0 loss=null; p99 без выборки=null |
| Новая сеть | При E=0 deliveryLoss=null; пустая гистограмма даёт null; скорости не определяются, если measurement не завершён |

В предлагаемом научном чтении нулевой знаменатель обозначается как «не оценивается» с сохранением исходного машинного значения. Ноль из программного соглашения не доказывает отсутствие ошибок или недоставки. Отдельно различаются: показатель неприменим, применимая выборка не наблюдалась, запуск технически не завершён, критерий сравнения нарушен. Эти состояния не заменяют друг друга.

В текущем Web импорт требует A>0, C>0, P=0 и A=C+F для каждого из трёх натурных повторов. Модельная когорта может содержать P>0: `allCriteriaPassed` дополнительно требует `outcomesSettled=true`, даже если отдельные числа укладываются в пороги. При нулевом эталоне относительная ошибка получает `notApplicable`, а не `passed`.[W1], [W2]

Сохранённые допуски сравнения не меняются: относительная ошибка RPS ≤15%, публикационного p99 QoS 1/2 ≤20%, абсолютная разность долей failure и loss ≤0,05, то есть пять процентных пунктов. Новый Web сравнивает модель с арифметическими средними трёх натурных значений по каждому показателю. Импорт проверяет формат, SHA и связность метаданных с профилем; истинность загруженных натурных счётчиков и их пересчёт из первичных журналов остаются за внешней проверкой. Без пакета контроля адаптер использует калибровочный профиль, что не является новым независимым натурным контролем.[W2]

## 5. Публикационная задержка, получение и RTT

| Показатель | Начало и конец интервала | Применимость |
| --- | --- | --- |
| p99 завершения публикации | Натура: длительность успешного Publish API. Когортная одиночная модель: от модельного начала публикации до успешного исхода | QoS 1/2; не задержка subscriber и не изолированное время CPU брокера |
| Сетевой `publishP99Ms` | Общая гистограмма завершений отслеживаемых исходных publishers | QoS 1/2; внутренние forwards в эту исходную гистограмму не подставляются |
| Сетевой `receiverP99Ms` | От создания исходного ID перед API-попыткой до первого получения ожидаемой пары | Все QoS, включая QoS 0; только реально полученные пары |
| Задержка первого получения в натуре | От зарегистрированной попытки до первого известного получения по общим workload-часам | Вычисляется отдельно из журналов при наличии сопоставимых часов; не является `publishLatencyMs` |
| RTT baseline | Отдельный контрольный обмен туда и обратно | Самостоятельное исходное измерение, не замена любого из двух p99 |

Для QoS 0 нет публикационного подтверждения: соответствующий p99 неприменим, сохраняется null/`notApplicable`. Это не нулевая задержка. Задержка получения QoS 0 при этом измерима. В новом Web одиночная проверка и импорт контроля ограничены QoS 1/2, payload 16 байт и одним subscriber; QoS 0 нельзя считать уже поддержанным этим путём.[W2], [W3]

Во всех рассмотренных пересчётах используется ближайший верхний ранг: элемент `ceil(0,99×n)` упорядоченной выборки, начиная с первого. Модельные гистограммы имеют разрешение tick и переводятся в миллисекунды. p99 без выборки не равен нулю. Среднее трёх p99 описывает три повтора; оно не равно p99 объединённой выборки. Гистограмма профиля может объединять наблюдения иначе. В сетевом p99 получения нет задержек недоставленных пар: рядом нужна полнота, чтобы малый p99 немногих получений не выглядел хорошей доставкой.[A1], [N1], [B4]

## 6. Прогрев, drain и повторы

Warmup подготавливает систему; его ID исключаются из измерительной когорты. Это проверяется идентичностью публикаций, а не близостью времён к границе. Measurement задаёт подачу основной нагрузки. Drain наблюдает уже начатую работу без новой основной нагрузки. Cooldown натурной кампании — отдельная пауза после результата.

Обычный Benchmark заканчивает drain по полной доставке успешных ID, таймауту или quiet period. В согласованной серии статьи 1 и соответствующем Web включено полное фиксированное окно наблюдения; quiet period не сокращает его. Незавершившиеся к горизонту исходы должны оставаться видимыми в пересчёте, а выход натурных исходов за фиксированный горизонт является ошибкой исполнения.[B3], [B5], [W3]

В сетевой программе сначала выполняется `warmupDrain` до простоя, затем сбрасываются брокерные счётчики. Получения warmup ID дополнительно исключает реестр. После measurement выполняется drain до простоя с заданным пределом; `uniqueBeforeDrain/uniqueDuringDrain` и `sourceCompletedBeforeDrain/sourceCompletedDuringDrain` показываются отдельно. В прежнем общем Relay простой reset счётчика receiver не исключает поздние warmup-получения; в исходнике это ограничение явно записано как `receiverScope`.[N2], [N3], [M2]

Модельные секунды не равны времени выполнения на компьютере. Wall time, total ticks, steps и память процесса симулятора описывают стоимость вычисления. Они не заменяют T_submit и ресурсы моделируемого брокера. Точный повтор одного seed проверяет воспроизводимость; разные seed не являются новыми независимыми натурными измерениями. Для средней точки следует сохранять число пригодных повторов и способ объединения; min–max трёх seed не называется доверительным интервалом.

## 7. Дубликаты и неожиданные получения

В Benchmark `duplicateDeliveries` — все получения после первого для каждого ID, включая неизвестные ID; `unexpectedDeliveries` — число событий получения неизвестных ID. `uniqueDeliveries` включает только известные ID. В пересчёте статьи 1 `duplicates` считает повторы внутри выбранной когорты и горизонта, а остальные события относятся к `outsideCohortDeliveryEvents`. Это разные области счёта.[B2], [A1]

В сети `duplicateDeliveries` — повтор уже учтённой пары «ID, receiver», а `suppressedDuplicates` — отфильтрованные федерацией повторные импорты. Подавленный повтор не является доставленным дубликатом. `unknownDeliveries`, `unexpectedDeliveries`, `queueDrops`, `hopLimitDrops`, `forwardRejected` сохраняют разные причины и уровни учёта; их нельзя суммировать как уникальные потерянные сообщения без ID-сопоставления.[N2], [N3]

## 8. Пересылки, topic+payload и физический транзит

`forwardAttempts` считает логические попытки межброкерного экспорта, `forwardAccepted/forwardRejected` — их исходы на соответствующем интерфейсе. `forwardTopicPayloadBytes` суммирует `UTF8(topic).Length + payloadBytes` по таким попыткам, включая отклонённые. Это не только payload, не Ethernet-трафик и не сумма байтов всех физических переходов.[N1], [N2]

Для звезды основной сети есть отдельный снимок `network-evidence`: разности `Inbound`, `Outbound`, `TransferPackets` и других доступных счётчиков узла transit между окончанием warmupDrain и окончанием measurement+drain. Данные входа и выхода могут относиться к одной передаче: их сумма не означает объём уникальных данных. Эти байты включают доступный модельный служебный обмен и не равны topic+payload. Один логический экспорт может пройти несколько физических участков. Проверка transit не восстанавливает стоимость всех рёбер линии и кольца.[N4], [N5]

## 9. CPU, RSS и EST

CPU и RSS в натурном сравнении относятся к реальному процессу брокера. `captureCpuMeanPercent/captureRssMaxBytes` описывают весь захват телеметрии. Для итогового сравнения `cpuPercent` — среднее, взвешенное по длительности пригодных внутренних интервалов нагрузки; `rssMaxBytes` — максимум выбранных отсчётов, а не гарантированный пик между ними. Сборщик исключает граничные интервалы с учётом точности UTC и требует не менее 15 с пригодного покрытия. CPU нормирован на одно закреплённое логическое CPU; процент для EST делится на 100. MiB=2²⁰ байт.[R1]

Одиночный двойник и сетевая модель не моделируют CPU/RSS настоящего брокера. Расход ресурсов самого MqttY/Web или мониторинг контейнера сервера характеризуют исполнение расчёта. Их нельзя подставлять вместо натурных CPU/RSS в EST. Для основной сети и нового Web готовая оценка EST в просмотренном пути не вычисляется.

Для прежней натурной серии применяется:

`EST = ¼×R/max(R_B) + ¼×(1−U_cpu) + ¼×(1−L/max(L_B)) + ¼×S_attempt`.

Здесь R — средний completed RPS, U_cpu — средняя доля CPU, L — среднее публикационное p99 QoS 1/2, S_attempt — среднее `D_id/A` по повторам. Буква C для CPU и F для недоставки из старой записи формулы здесь заменены словами/отдельными обозначениями, чтобы не смешать их с количеством завершений и ошибок. Это запись той же формулы, а не новый критерий.[E1]

Максимумы R и L берутся по четырём брокерам внутри одной одинаковой нагрузочной точки после усреднения повторов; затем оценки усредняются по сетке. Строгая четырёхкомпонентная EST относится к 16 точкам QoS 1/2. В EST* для QoS 0 член L исключён, три оставшихся веса равны 1/3; общий итог относится ко всем 24 точкам. При max R=0 вклад R равен 0; при наблюдённых применимых L и max L=0 вклад задержки равен 1. Отсутствующие обязательные наблюдения не заменяются нулями. Проверочный код ограничивает CPU сверху единицей при допустимой погрешности представления; это не разрешение использовать CPU с другой нормировкой.

EST — выбранная интегральная оценка с заданными весами. Она не является вероятностью надёжности, точностью двойника или тестом достоверности данных. Изменение весов, брокеров либо сетки может изменить рейтинг. Доставочный член `D_id/A` не равен `Dс/C` или `D_pair/E`.[E1]
