# Программа более длинных сетевых опытов

Программа продолжает техническую проверку Relay и статической федерации. Конфиги подготовлены и проверены CLI, но опыты ещё не выполнены. Сначала нужны pilots, их стоимость и проверка достаточности фаз. Короткая прежняя серия не засчитывается как новая матрица.

## Задача и общее устройство

Сравниваются `single`, `relay` и `federation` при одинаковой физической сети, размещении клиентов и заданной исходной нагрузке. Различия числа брокеров, служебных соединений, очередей и параллелизма учитываются явно. Это исследование механизма доставки; равный аппаратный бюджет и натурная точность сети не заявляются.

`Federation.App` строит опыт и запускает фазы. Ядро MqttY выполняет время, очереди и пакеты. MqttRelay и StaticFederator пересылают сообщения по своим правилам. MqttBenchmark в этой серии не запускается. Внешний сценарий должен сохранять команды, входы, stdout/stderr, попытки и результаты независимой проверки.

| Условие | Кандидат программы |
| --- | --- |
| Площадки и брокеры | 4 площадки; 1 центральный брокер в single, по брокеру на площадку в остальных режимах |
| Publishers | Всего 64, по 16 на площадке; в single клиенты остаются на своих площадках |
| Получатели | По одному на площадке; каждый ожидает все источники |
| Основная модель | Идеальная, без профиля настоящего брокера |
| Физические сети | Линия, кольцо, звезда с пустым транзитным узлом |
| Исходная суммарная интенсивность | 1000 и 5000 публикаций/с; это не измеренная предельная производительность |
| Payload и QoS | 16 байт; QoS 0/1/2 |
| Seeds | 42/43/44 |
| Tick | 0,1 мс; не смешивать с шагами отдельной проверки BrokerFidelity |
| Фазы основной матрицы | Прогрев 1 с, измерение 10 с, drain до 5 с модельного времени |
| Фазы pilots | Измерение 2 либо 10 с; остальные длительности те же |
| Сетевые допущения | 125000000 байт/с, окно пропускной способности 100 ticks, передача 2 ticks, очередь 100000 |
| Федератор | FIFO выхода 1024, кэш ID 100000, лимит переходов 4 |

Параметры сети остаются модельными допущениями. FIFO федератора не приписывается Relay: Relay вызывает Publish непосредственно, а принятие/отказ фиксирует наблюдаемый MQTT-клиент. В самой нагруженной конфигурации запланировано 55000 ID с прогревом, до 220000 пар доставки; бюджеты кэша и приложения не превышены. Это не оценка байтов диска или RSS.

## Количество запусков

| Группа | Расчёт | Запуски |
| --- | --- | ---: |
| Pilots для длительности и нагрузки, QoS 1 | 2 физические сети × 3 режима × 2 интенсивности × 2 окна; seed 42 | 24 |
| Дополнительные pilots QoS 0/2 | Звезда × 3 режима × 2 QoS, 5000/с, окно 10 с | 6 |
| Основная идеальная матрица | 3 физические сети × 3 режима × 3 QoS × 2 интенсивности × 3 seeds | 162 |
| Побайтные повторы | Звезда, QoS 2, seed 42: 3 режима × 2 интенсивности | 6 |
| Необязательная диагностика Mosquitto | Кольцо × 3 режима × 3 QoS × 2 интенсивности × 3 seeds | 54 |

Обязательная предложенная программа — **30 pilots + 162 + 6 = 198 симуляций**. Ещё 54 конфигурации подготовлены отдельно; они не должны автоматически попасть в основную матрицу. Все 252 JSON прошли команду `validate`; это **ноль выполненных симуляций**.

Диагностика использует snapshot Mosquitto: N=64 в single, N=16 на распределённый брокер. Пересылки и дополнительные соединения выходят за натурную калибровку. Эти результаты не доказывают точность реальной федерации. Десятиброкерная сеть и недостающая точка профиля N=160 не добавляются в программу скрыто.

## Условие перехода от pilots к матрице

После завершения текущей серии чувствительности на Linux:

1. Зафиксировать чистые commits, программу, конфиги, проверяющий код и snapshot runtime с SHA. Создать новый каталог на смонтированном диске доказательств; прежние выходы не перезаписывать.
2. Запустить только pilots, первоначально с одним worker. Проверить payload, пары доставки, пересылки, очереди, backpressure и причины незавершённых фаз. Технический отказ останавливает новые задачи и сохраняет попытку.
3. Сравнить окна 2 и 10 с: показатели строго внутри окна и итоговые с drain; число наблюдений, задержки, относительную долю хвоста и динамику во времени. Проверить, что прогрев не смешан с измерением по ID.
4. Замерить wall time, peak RSS и объём полных журналов. Рассчитать бюджет основной матрицы по группам, с запасом места и учётом параллелизма. До этих замеров честного прогноза Linux-времени для новой сети нет.
5. Зафиксировать решение о достаточности фаз. Если виден переходный режим, так его и описывать; при изменении программы создать следующую версию, не переписывая pilots. Не объявлять установившуюся или предельную производительность только по длине окна.
6. После принятия программы выполнить 162 + 6; необязательные 54 запускать отдельной серией с отдельным выводом.

Три seeds в идеальной детерминированной модели могут давать одинаковые результаты. Их нельзя считать независимыми случайными наблюдениями и превращать нулевой разброс в доказательство высокой статистической точности. Для p99 показываются размер выборки и число хвостовых наблюдений; небольшой объём требует осторожной интерпретации.

Существующие журналы позволяют разложить по времени исходные попытки и получения. Для такой же динамики завершений ACK нужны дополнительные снимки счётчиков или события завершения: одного итогового p99 и суммарного RPS недостаточно. Это нужно учесть в runner до приёмки pilots как проверки установившегося режима.

Основные выходы: исходные попытки и завершения, доставки на получателя, полнота, доля дошедших всем, ACK для QoS 1/2, задержка получения, пересылки/байты, повторы, очереди и drain. Отдельно сохраняются physical/logical SVG/Mermaid и фактический граф. Формулы проверяются по первичным журналам, а не только по summary.

После запуска длительной фоновой задачи агент подтверждает службу/PID, сохраняет журнал прогресса и останавливается до ручного продолжения. Новую сетевую серию не запускать одновременно с текущей чувствительностью: это затруднит интерпретацию стоимости расчёта.

## Подготовка и состояние реализации

```text
python tools/dissertation/prepare_network_study.py --output <новый-каталог-программы>
python -m unittest discover -s tools/dissertation -p test_prepare_network_study.py -v
dotnet <snapshot-runtime>/EntityFX.MqttY.Federation.App.dll validate --config <конфигурация.json>
dotnet <snapshot-runtime>/EntityFX.MqttY.Federation.App.dll run --config <конфигурация.json> --output <новый-каталог-опыта>
```

Генератор создаёт переносимые относительные пути к копии профиля, по одному JSON на точку, связи повторов с оригиналами и SHA файлов. Он не запускает модели. Подготовленный пакет: [plan.json](../../reports/audits/dissertation/network-study-v1/plan.json), [валидация 252 конфигураций](../../reports/audits/dissertation/network-study-v1/configuration-validation.json).

Шаг 21 подготовлен частично: программа и проверка конфигов есть, Linux-pilots и их оценка ещё впереди. Для шага 22 реализован [отдельный оркестратор](network-runner.md): snapshot, resume, ограничения ресурсов, проверка первичных журналов, бюджет диска и сохранение частичного отказа. Пройдены локальные тесты; Linux-preflight ещё не выполнен. После этого можно выполнять шаги 23–24: матрицу, повторения и графики. Проценты плана за эти незавершённые шаги пока не увеличиваются.
