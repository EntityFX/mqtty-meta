# Статическая федерация брокеров: состав и проверка

Реализуется отдельный проект `EntityFX.MqttY.Federation.App` в существующем solution MqttY. Он сравнивает один центральный брокер, сеть с MqttRelay и статическую федерацию. Исходные брокеры не запускаются: используется идеальная модель либо snapshot профиля настоящего брокера.

## Кто что делает

| Часть | Ответственность |
| --- | --- |
| MqttBenchmark и calibrate | Заранее получить измерения и профиль |
| Federation.App | Проверить входы, построить сеть, задать нагрузку, выполнить фазы и сохранить результаты |
| Ядро MqttY | Исполнить время, физическую сеть, очереди и MQTT-обмен |
| StaticFederator | Получать исходные сообщения, подавлять повторные ID, пересылать соседям и доставлять локальным subscribers |
| Существующий MqttRelay | Пересылать по заранее настроенным деревьям без циклов |
| Сценарий tools/federation/study.py | Выполнить приёмочную серию, независимо проверить журналы и подготовить отчёт |

Исходный клиент публикует в input, федераторы используют routing, а subscriber подписан на delivered. Payload не меняется; служебные поля входят в тему и занимают место в сети. Каждая пересылка выполняется через модельные MQTT-клиенты. Кэш ID хранится до конца ограниченного опыта, очереди и число переходов ограничены. Переполнение и недоставка показываются явно.

## Как запустить

Команды из корня мета-репозитория:

```text
dotnet run --project mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.Federation.App -c Release -- demo --brokers 3 --mode federation --topology ring
dotnet run --project mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.Federation.App -c Release -- demo --brokers 3 --mode relay --topology ring
dotnet run --project mqtty/src/EntityFX.MqttSimulator/EntityFX.MqttY.Federation.App -c Release -- validate --config docs/examples/federation/mosquitto.json
```

Демо не требует конфига и профиля; без `--output` файлы не создаются. Для сохранения опыта используется `run --config <json> --output <новый-каталог>`. Для матрицы — `matrix` с теми же аргументами: три режима × три QoS × seeds 42/43/44 = 27 опытов. Путь профиля разрешается относительно JSON.

Подробные параметры и формулы находятся в README приложения. Для другой машины нужны .NET SDK с поддержкой net6.0 и .NET 6 runtime. Python требуется только сравнительному сценарию и графикам, а не демонстрации приложения.

## Приёмка и ожидаемый результат

Проверяются линия, кольцо и ромб; QoS 0/1/2; локальные и удалённые subscribers; отсутствие subscribers; одинаковые номера у разных источников; циклы, переполнения и drain; сохранность payload и повторение расчёта. Регрессионные тесты старых приложений должны проходить.

Серия содержит **27 идеальных + 27 профилированных симуляций** и шесть повторов. Идеальная часть: три площадки, 12 publishers; Mosquitto: четыре площадки, 64 publishers, точные профильные N=16/N=64. Нагрузка 1000 сообщений/с; прогрев 0,01 с; измерение 0,2 с; drain до 1 модельной секунды; tick 0,1 мс. Каждый subscriber должен получать публикации всех источников, а фактические недоставки сохраняются как результат.

Ожидаемый результат — отчёт со сравнением доставки, исходных завершений, задержек и накладных расходов; CSV/JSON для пересчёта; схемы физической сети и логических маршрутов; совпадение scientific summaries повторных запусков. Успех процесса не означает полной доставки или натурной точности.

## Границы

Программа не воспроизводит самоорганизующуюся федерацию статьи Ribas–Spohn: нет выбора ядра, beacons, объявления членства, No Local и перестроения после отказа. Связи задаются заранее, а клиентам требуется соглашение о темах. Исходный подход: https://thescipub.com/pdf/jcssp.2022.687.694.pdf.

Профиль настоящего брокера не подтверждает точность при дополнительной пересылке и fanout. Нет оценки CPU/RSS, EST и доказательства отказоустойчивости. Приёмочная матрица короткая: для исследования предельной производительности и натурной валидации нужна отдельная программа. Существующие кампании, отчёты и архивы не изменяются; полные новые архивы хранятся вне Git.
