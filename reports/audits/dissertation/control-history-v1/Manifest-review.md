# Проверка исторических manifests из архивов

Продолжение [первого аудита истории](Review.md). Новые симуляции и натурные измерения не запускались. Четыре архива модельных доказательств прочитаны на Linux без распаковки на системный диск; их полные SHA-256 совпали с ранее опубликованным реестром.

| Проверка | Покрытие | Результат |
| --- | ---: | --- |
| Хэши архивов | 4/4 | Совпали с ожидаемыми значениями |
| Идентификаторы запусков, config SHA и manifest SHA | 864/864 | Совпали с опубликованным model-evidence.json |
| Версия исходников MqttY в provenance | 864/864 | Указан commit 115885e012053d0112413e07743b061369ebea93 |
| Профили и калибровочные observations | 864/864 | Соответствуют выбранным данным каждого брокера |
| Ссылки на контрольные observations | 288/288 holdout | Соответствуют выбранным validation observations |
| Идентичность исполняемой сборки | 0/864 | В прочитанных manifests отсутствуют поля бинарного SHA/сборки |

Для каждого брокера проверены 72 Fidelity, 72 holdout и 72 Relay-опыта. Все сопоставления метаданных прошли; восемь тестов локального проверяющего скрипта покрывают повреждение, дубли, пропуски, подмену commit, runId, профиля и наблюдений. Проверенные хэши и источники сохранены в [экспорте](../../../status/control-manifest-observation.json), решения — в [manifest-verification.json](manifest-verification.json).

Слой проверок разделён: чтение архивов на Linux проверило их байты и экспортировало поля; Python-проверка на Windows сопоставила экспорт с опубликованным реестром. Поэтому в JSON локального проверяющего `archiveBytesVerified=false`: сам этот скрипт архивы повторно не открывал. Это не означает несовпадения архивов в предыдущем слое.

**Вывод:** устранена неопределённость о содержимом исторических manifests и заявленной ими версии исходников. Прямое доказательство исполнения конкретной DLL остаётся неполным. Commit и версия .NET не заменяют бинарный SHA; добавить отсутствующий хэш задним числом как исторически записанный нельзя.

Следующий допустимый шаг — проверить сохранившиеся журналы развёртывания и snapshots runtime. Если надёжной привязки не найдётся, ограничение останется в методике; для будущих опытов следует записывать хэши исполняемого приложения и зависимостей до начала расчёта. История первого просмотра прежних контрольных данных остаётся отдельным вопросом. Согласованность 864 записей не доказывает слепую проверку и не меняет 85 провалов точности из 288 holdout.

## Повторение

На машине, где доступны исходные архивы, выполнить из корня мета-репозитория:

```sh
python3 tools/dissertation/export_control_manifests.py --archive-registry reports/audits/dissertation/archives.json --output /path/to/new-export.json
python3 tools/dissertation/control_manifest_audit.py --export /path/to/new-export.json --model-evidence reports/data/model-evidence.json --repository-root . --output /path/to/new-verification.json
```

Пути архивов читаются из реестра. Оба выходных файла должны быть новыми; архивы не распаковываются. Повторный реальный экспорт на Linux дал те же 864 записи полей и хэшей; время наблюдения сравнивать побайтно не требуется. [Повторный экспорт](reproduced-export.json) и [повторная проверка](reproduced-verification.json) сохранены. Аудитор и экспортер проверены 14 тестами. Ни успешный повтор, ни source commit не восстанавливают отсутствующую историческую запись бинарного SHA.
