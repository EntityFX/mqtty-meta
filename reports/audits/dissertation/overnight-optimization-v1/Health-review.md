# Раннее обнаружение технических проблем

## Что проверено

Существующий `tools/status/monitor_sensitivity.py` читает результаты на Linux и выводит их в терминал. Он не сохраняет снимок состояния на Windows, поэтому его работа сама по себе не создаёт локального источника для последующего анализа. Пользовательский файл не изменён.

В показателе `fail` и красной ячейке смешаны два разных события: нарушение критериев точности и технический отказ. Успешно завершённая модель может не пройти критерий точности. Такой результат нельзя автоматически перезапускать или исключать из сравнения.

Прогноз монитора — линейная экстраполяция числа завершённых заданий. Он объединяет короткие и длинные опыты, использует время пилотов и не учитывает ожидание конца пары в исходном планировщике. Его следует показывать как ориентир, а не гарантированный срок. Низкая общая загрузка CPU при одном активном однопоточном опыте сама по себе не доказывает зависание.

Чтение `/proc/stat` включает `guest` и `guest_nice`, уже входящие в другие поля; при виртуализации возможен небольшой двойной учёт. Датчик `hwmon0/temp1_input` выбран без проверки имени устройства: значение не всегда является температурой пакета CPU. Отсутствие RAPL-показателя означает отсутствие доступного измерения, а не нулевое энергопотребление. Эти данные пригодны для наблюдения за ресурсами; они не являются научными метриками сравнения брокеров.

## Реализованная проверка

Добавлен отдельный `tools/status/sensitivity_health.py`. Он не подключается по SSH, не запускает циклический опрос и не останавливает процессы. На Windows проверяет готовый JSON-снимок; на Linux может однократно собрать снимок из `progress.json`, неизменяемого плана, systemd, `/proc` и сведений о диске.

Проверки:

- раздельный учёт технических ошибок и нарушений критериев точности;
- возраст снимка и отдельно задержка изменения `progress.json`;
- остановленная служба при незавершённой программе;
- отсутствие активного PID при проверке, с предупреждением о возможной смене задания между чтениями;
- достижение 80% лимита времени или памяти и отдельно превышение лимита;
- наличие mount и достаточность свободного места относительно заданного резерва;
- сохранение ошибок сбора и неизвестных значений вместо подстановки «всё исправно».

Отчёт содержит наблюдённое время и признак актуальности. Предупреждение по старому снимку описывает прошлое состояние. Оно не подтверждает, что процесс сейчас работает или сейчас остановлен.

## Как использовать

На Linux, один снимок без постоянного опроса:

```sh
python3 tools/status/sensitivity_health.py \
  --root /путь/к/смонтированному/диску/кампания \
  --mount /путь/к/смонтированному/диску \
  --service mqtty-sensitivity-v1.service \
  --save-snapshot /путь/к/новому-снимку.json
```

Анализ уже полученного файла на текущем хосте:

```sh
python tools/status/sensitivity_health.py --snapshot снимок.json
```

`--save-snapshot` создаёт новый файл и отказывается перезаписывать существующий. Если основной монитор будет сохранять снимки сам, ему достаточно экспортировать этот же набор полей; дополнительное SSH-соединение для проверки не требуется.

Минимальные поля: `observedAtUtc`, `progress`, `progressMtimeUtc`, `service`, `processes`, `mountAvailable`, `disk.free`, `limits.timeoutSeconds`, `limits.maxRssBytes`, `limits.minFreeBytes`. Неизвестные поля допускаются; отсутствие обязательного для конкретной проверки наблюдения отмечается явно. Исходный план v1 задаёт 1800 секунд на попытку и индивидуальный предел RSS; резерв диска v1 — 5 GiB. Изменение эксплуатационных лимитов отдельным планировщиком необходимо отражать в новом снимке, сохраняя происхождение значений.

## Проверки и ограничения

В `test_sensitivity_health.py` проверяются 16 сценариев: разделение ошибок и критериев, устаревание, остановленная служба, гонка с PID, пороги ресурсов, отсутствие mount, неполные данные, неизменность входного снимка, экспорт без перезаписи, сбор данных и границы каталога. Все тесты проходят на текущем хосте. Дополнительно выполнен настоящий однократный сбор на Linux после переключения: служба active/running, четыре живых PID, mount доступен, ошибок сбора нет. Снимок сохранён в `reports/status/sensitivity-scheduler-v2-health.json`; он подтверждает только состояние на указанное в нём время.

Существование PID не подтверждает его принадлежность именно сохранённой попытке: номер может быть использован повторно. Сохраняется `startTicks`, но для строгого сопоставления нужен такой же идентификатор в записи первоначального запуска. Исчезнувший PID не позволяет установить код завершения чужого дочернего процесса. Нет оснований подменять его успехом или автоматически повторять опыт.

Частота обновления снимка и проверки времени должна быть заметно меньше оставшегося резерва до технического лимита. Проверка раз в несколько секунд обнаружит приближение к лимиту, но не ускорит саму модель. Для ускорения нужен планировщик, который сразу занимает освободившийся слот, ограничивает общую память и сохраняет результаты каждой завершённой попытки. Проверка состояния — наблюдение и основание для разбирательства; восстановление должно быть отдельным явно разрешённым действием с новой попыткой и сохранением старой.
