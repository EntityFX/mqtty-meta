2. Верификация RPS и остальных метрик

Новый проверяющий скрипт использует стандартную библиотеку Python и отдельную скалярную реализацию формулы. Он не вызывает функцию оценки из генератора основных отчётов. Результаты пересчёта и SHA-256 входов · Код проверки.

Обозначения одного натурного запуска: A — попытки публикации, P — успешно завершённые вызовы, E — ошибки вызовов, D — уникальные получения, D_P — полученные ID среди успешно завершённых публикаций, T — фактическое время измерения. Буква C ниже в формуле EST обозначает загрузку CPU.

Показатель Независимо проверенная формула Что именно измеряет
Attempted RPS A / T Частоту вызовов, включая быстрые локальные ошибки; не гарантированно число сообщений в сети
Completed RPS P / T Завершения PublishAsync; для QoS 1/2 это публикация с подтверждением, а не получение подписчиком
Publish failure E / A Долю неуспешных вызовов публикации
Delivery loss 1 − D_P / P Отсутствие получения к концу наблюдения среди завершённых публикаций
Успешность доставки для EST D / A Получения относительно всех попыток; включает влияние неуспешных локальных вызовов
p50/p95/p99 Среднее соответствующих перцентилей трёх повторов Задержку завершения публикации QoS 1/2; не сквозную задержку доставки
RTT Среднее трёх отдельных измерений baseline Опорное время обмена, не p99 рабочей нагрузки
CPU Среднее процесса по длительности внутренних интервалов нагрузки Долю одного закреплённого логического CPU
RSS Максимум наблюдённых внутренних отсчётов Выборочную, а не непрерывно измеренную пиковую память процесса

Повторно проверены 2304 значений RPS/failure/loss у 576 запусков, 768 групп «среднее / SD / CI» и 384 средних перцентилей. Проверены A=P+E, разбиение полученных ID на исходы публикации, сумма причин ошибок и полное покрытие повторов.

При чтении внешних архивов: 576 комплектов файлов с внутренними контрольными суммами и 1152 повторных вычислений CPU/RSS. Seals сверены для извлечённых результатов, телеметрии и guard. Это не новый пересчёт всех первичных журналов сообщений. Прежний подробный аудит охватил 24 raw-архива ActiveMQ и не пересчитывал p99. Границы этого аудита.

Время и единицы

Фактическое натурное окно T находится в диапазоне 20.000106–29.920572 с, хотя плановая нагрузка — 20 с. Последний начатый вызов может завершиться позже границы. Деление на 20 вместо сохранённого T изменило бы RPS. В симуляторе знаменатель фиксирован: 2 с; завершающиеся при drain операции учитываются по правилам модели. Знаменатели необходимо сохранять явно при сравнении.

CPU-сэмплы имеют UTC с точностью до секунды, поэтому в расчёт включены только интервалы, гарантированно лежащие внутри нагрузки; вес — их монотонная длительность. Граничные интервалы исключены. Guard 99% относится к контролю нагруженности стенда и не гарантирует отсутствие влияния общего хоста. Привязка к логическому CPU не означает выделенное физическое ядро.

Статистическая неопределённость

Для среднего трёх повторов: CI95 = mean ± 4,30265273 × s / √3, две степени свободы. Проверена арифметика этой формулы. Независимость повторов, стационарность стенда и подходящая форма распределения при n=3 не доказаны. CI не является интервалом задержек 95% сообщений. Среднее p99 повторов не равно p99 объединённых сообщений. Натурный и модельный способы построения распределений также различаются.

3. Точность двойников брокеров

Затем получены 72 новых успешных натурных измерения и 72 контрольные симуляции при неизменном профиле. Известные контрольные результаты нельзя использовать для настройки и повторно называть их слепым независимым контролем.

5. Проверка EST при K_R=K_C=K_L=K_F=0,25

EST = 0,25 × R/max(R_B) + 0,25 × (1−C) + 0,25 × (1−L/max(L_B)) + 0,25 × (1−F)

Для одной точки R — средний completedRps; C — средняя доля CPU процесса; L — среднее p99; 1−F — среднее D/A. Максимумы берутся по четырём брокерам в той же комбинации байт/QoS/отправителей. Члены рассчитываются после усреднения трёх повторов, затем оценки усредняются по точкам. Нормировка, набор брокеров и порядок усреднения являются частью метода.

Строго исходная четырёхкомпонентная формула применима к 16 точкам QoS 1/2. Для восьми точек QoS 0 нет L подтверждения; подстановка нуля необоснованно улучшила бы оценку. В прежнем общем EST* член L исключён и три оставшихся веса равны 1/3. Это другая, явно обозначенная оценка.

Брокер EST: QoS 1/2, четыре веса 0,25 EST*: все QoS, адаптация Bootstrap 95% для EST*
Aedes 0.5058 0.5520 0.5461–0.5572
Mosquitto 0.5694 0.5623 0.5571–0.5663
ActiveMQ 0.2392 0.2459 0.2378–0.2537
EMQX 0.4918 0.4505 0.4457–0.4551

Новый независимый скалярный пересчёт совпал со всеми 96 опубликованными оценками «брокер/точка» и четырьмя общими средними. Лидер обоих вариантов — Mosquitto. При повышенном весе доставки 0,55 лидирует Aedes, поэтому выбор зависит от цели. Подробная чувствительность и исходные компоненты: сравнение, CSV.

Что доказывает формула

Если R и L неотрицательны, знаменатели положительны, C и F лежат в [0;1], каждый нормированный член лежит в [0;1]. При неотрицательных весах с суммой 1 их взвешенная сумма также лежит в [0;1]. Это математическое свойство шкалы. Оно не доказывает правильность входных измерений, достаточность повторов или объективность весов. Совместная независимость R/C/L/F для вычисления суммы не требуется; считать эти свойства статистически независимыми оснований нет.

Максимум L делает вклад задержки худшего брокера нулевым; наличие выброса меняет относительные оценки остальных. Изменение набора сравниваемых брокеров меняет максимумы и может изменить рейтинг. Низкая загрузка CPU вследствие простоя сама по себе не равна эффективности. Время и стоимость плохой доставки могут быть недооценены суммой: высокая скорость способна компенсировать loss. Для выбора под SLA сначала необходим отдельный допустимый предел недоставки, а затем рейтинг допустимых вариантов.

Доверие к рейтингу

Опубликованный bootstrap использует 2000 выборок с seed 20261019: целые повторы выбираются с возвращением внутри каждой фиксированной пары «брокер/точка», связанные метрики сохраняются вместе и максимумы пересчитываются. Он отражает только разброс трёх имеющихся повторов при данной сетке. Междневной дрейф, ошибки генератора, смена hardware и систематические ошибки в него не включены. Частоту первого места в bootstrap нельзя объявлять вероятностью того, что брокер лучший вообще. Для строгой четырёхкомпонентной оценки отдельный bootstrap-интервал здесь не рассчитывался; интервалы в таблице относятся только к EST*.

EST=0,562 не означает ни 56,2% достоверности, ни 56,2% успешных доставок. Это положение в выбранной системе нормирования. Условный рейтинг арифметически проверяем; универсальное превосходство Mosquitto данными этой серии не доказано.

6. Как проверить другим сотрудником

Для проверки расчёта по опубликованным JSON достаточно Python 3.11+ и репозитория с подмодулями:

python tools/campaign/assess-evidence.py --reports reports

Для проверки извлечённых sealed members, CPU/RSS и SHA-256 внешних архивов добавьте их каталог:

python tools/campaign/assess-evidence.py --reports reports --archive-root <каталог-архивов>

Реестр архивов на диске результатов. ZIP намеренно исключены из Git. Режим без --archive-root подтверждает арифметику JSON, а не повторное чтение первичных архивов. Полный пересчёт ID всех сообщений требует оригинальных raw ZIP из реестра кампании, а не только компактных native-members.zip.

Для повторения модели используйте сохранённый config из внешнего модельного архива, тот же runtime, SHA-256 профиля и seed. Меняются только пути к источникам. Сравнивайте summary, histogram, научные counters и фазы, исключая служебные runId и время вычисления. Для выбранной шестёрки готов скрипт; для новой установки — руководство полной серии. Для независимой проверки после исправления модели нужен новый натурный контроль.

7. Что необходимо для более сильного заключения

  1. Пересчитать первичные ID и перцентили по всем raw-журналам; проверить MQTT-трафик отдельным приёмником или захватом пакетов в диагностических опытах.
  2. Исправить повторные вызовы отключённого клиента, разделить локальные ошибки и фактические сетевые публикации; собрать новую калибровку и новый контроль.
  3. Повторить граничные нагрузки с более длинным окном и другим шагом модели; заранее зафиксировать критерии и проверить новые данные без подбора профиля по контролю.
  4. Повторить выбранные и граничные точки независимым сотрудником на другой машине с фиксацией binary/config/profile SHA-256.
  5. Измерить настоящую Relay-сеть той же топологии с уникальными сквозными ID и сопоставить её с моделью.
  6. До нового опыта определить рабочую нагрузку, допустимую недоставку и веса EST; проверить устойчивость ранга на независимых днях, а не только в bootstrap текущих трёх повторов.

До этих проверок обоснованное заключение таково: сохранённые расчёты проверяемы, выбранные модельные запуски повторяемы, точность двойников имеет измеренные ограничения, а EST даёт условный выбор по явно заданным предпочтениям.
