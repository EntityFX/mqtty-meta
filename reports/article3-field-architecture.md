# Статья 3: Моделирование крупной сельскохозяйственной IoT-архитектуры в MqttY

**Дата:** ноябрь 2026  
**Статус:** проектная документация (план экспериментов, топологии, ожидаемые цифры)  
**Инструмент:** MqttY (симулятор MQTT-сетей), MqttBenchmark (опционально, для натурных профилей)

---

## 1. Постановка задачи

Требуется смоделировать крупную сельскохозяйственную IoT-архитектуру на базе MQTT:

- **Поля**: несколько полевых участков, каждое обслуживает один локальный (полевой) MQTT-брокер.
- **Оросительные установки**: на каждом поле от 5 до 10 устройств (IoT-контроллеры орошения, датчики влажности, насосы).
- **Сети поля**: обычно мобильный интернет (4G/LTE), плохой IoT-канал — высокая задержка, потери пакетов, ограниченная пропускная способность.
- **Региональные брокеры**: каждый собирает данные с нескольких полей.
- **Связь региональных брокеров**: региональные брокеры связаны между собой для отказоустойчивости (если один регион недоступен, данные перенаправляются через другой).

Цель моделирования: оценить доставку, задержку, сетевой трафик и устойчивость при разных топологиях связи между региональными брокерами.

---

## 2. Архитектура системы

```
Поле A (оросительные установки 5–10 шт.) → Полевой брокер A → Региональный брокер 1
Поле B (оросительные установки 5–10 шт.) → Полевой брокер B → Региональный брокер 1
Поле C ...                                                      → Региональный брокер 2
Поле D ...                                                      → Региональный брокер 2
                                                              ↕
Региональный брокер 1 ⇄ Региональный брокер 2 (отказоустойчивая связь)
```

### Компоненты модели

| Компонент | Описание | Количество (пример) |
|-----------|----------|---------------------|
| Оросительная установка | IoT-устройство: датчик + насос, публикует телеметрию, принимает команды | 5–10 на поле |
| Полевой брокер (Edge) | Локальный MQTT-брокер на поле, агрегирует установки поля | 1 на поле |
| Региональный брокер | Центральный брокер региона, принимает с нескольких полей | 1 на регион |
| Связь региональных брокеров | Канал отказоустойчивости между регионами | Ring / Mesh / Federation |

### Связи

- Установка → Полевой брокер: локальная сеть поля (мобильный интернет, QoS 0/1/2)
- Полевой брокер → Региональный брокер: канал между полем и регионом
- Региональный брокер ⇄ Региональный брокер: резервный канал отказоустойчивости

---

## 3. Топологии для моделирования в MqttY

В MqttY доступны следующие топологии и движки, которые подходят для этой архитектуры:

### 3.1 Star (звезда) — поля через один региональный брокер

Все полевые брокеры подключаются к одному региональному брокеру. Региональных брокеров может быть несколько, но каждый обслуживает свою группу полей, а регионы связаны между собой.

```
Поле 1 → Регион 1
Поле 2 → Регион 1
Поле 3 → Регион 2
Поле 4 → Регион 2
Регион 1 ⇄ Регион 2
```

**Когда использовать:** мало регионов (2–4), чёткое разделение по географии.

### 3.2 Ring (кольцо) — региональные брокеры в кольце

Региональные брокеры соединены в кольце. Данные могут идти по часовой или против часовой стрелки. При выходе одного региона из строя данные перенаправляются через обратное направление.

```
Регион 1 → Регион 2 → Регион 3 → Регион 4 → Регион 1
```

**Когда использовать:** отказоустойчивость важнее задержки, 3–6 регионов.

### 3.3 Line (линия) — региональные брокеры в цепочке

Региональные брокеры соединены цепочкой. Крайние регионы имеют по одному соседу, внутренние — по два.

```
Регион 1 → Регион 2 → Регион 3 → Регион 4
```

**Когда использовать:** линейная география полей (например, вдоль трассы или реки).

### 3.4 Mesh (полносвязная сеть) — все региональные брокеры связаны

Каждый региональный брокер соединён с каждым. Максимальная отказоустойчивость, но наибольший трафик.

```
Регион 1 ⇄ Регион 2 ⇄ Регион 3 ⇄ Регион 4 (все со всеми)
```

**Когда использовать:** критически важные данные, бюджет на трафик не ограничен.

### 3.5 Federation (статическая федерация) — MqttY Federation engine

Региональные брокеры работают как федераторы с подавлением повторов. Каждый регион обслуживает свои поля, а межрегиональная доставка идёт через федераторов с кэшем ID и hop-limit.

**Когда использовать:** много регионов (до 16 в MqttY Federation), нужно подавление дублей и контроль трафика.

## 5. Ожидаемые цифры и метрики

### 5.1 Нагрузка (MqttY: M = R × T)

При 90 установках, частоте 0.5 Гц, времени измерения 30 с:

```
M = 90 установок × 0.5 сообщений/с × 30 с = 1350 сообщений
```

При QoS 1 (4 пакета на путь LB) и длине пути 2 (поле → регион):

```
X ≈ 4 × M × (L+1) ≈ 4 × 1350 × 3 = 16 200 пакетов (только поля → регионы)
```

При межрегиональной связке (Federation star, B=4):

```
X_fed ≈ M × (8.08×B² − 11.98×B + 11.84) ≈ 1350 × (8.08×16 − 11.98×4 + 11.84) ≈ 1350 × 117.5 ≈ 158 625 пакетов
```

### 5.2 Доставка (D)

| Топология | D / M | Комментарий |
|-----------|-------|-------------|
| Field → Region (Star, идеальный канал) | ~100 % | Надёжный канал между полем и регионом |
| Field → Region (мобильный, потери 5 %) | ~95 % | Потери на канале поля |
| Регион → Регион (Ring, Federation) | ~99–100 % | Надёжный межрегиональный канал |
| Регион → Регион (при отказе одного региона) | ~80–90 % | Перенаправление через альтернативный путь |

### 5.3 Задержка (p99)

| Составляющая | Задержка | Комментарий |
|--------------|----------|-------------|
| Установка → Полевой брокер (мобильный) | 100–500 мс | Плохой IoT-канал |
| Полевой брокер → Региональный брокер | 50–150 мс | Канал поля-регион |
| Регион → Регион | 20–100 мс | Межрегиональный канал |
| **Итого (до регионального брокера)** | **150–650 мс** | p99, в зависимости от QoS и потерь |
| **Итого (с отказоустойчивой пересылкой между регионами)** | **200–750 мс** | +一つ дополнительный hop |

## 10. Резюме первой задачи

Архитектура «Поле → Полевой брокер → Региональный брокер → Связанные региональные брокеры» моделируется в MqttY с использованием Federation engine и топологий Star/Ring/Line/Mesh. Ожидается, что:

- **Star** проще реализовать, но имеет единственную точку отказа на уровне региона.
- **Ring** даёт хороший баланс трафика и отказоустойчивости для 3–6 регионов.
- **Mesh** максимизирует отказоустойчивость, но увеличивает трафик O(B²).
- **Federation** подходит для до 16 регионов с подавлением дублей и контролируемым трафиком.

Для сельскохозяйственных IoT-полей с плохим мобильным каналом рекомендуется комбинация **Ring** между региональными брокерами (отказоустойчивость) и **QoS 1** на каналах поля (баланс надёжности и накладных расходов).

# Часть 2. Городская сеть IoT климата (здания, этажи, климатические датчики)

## 11. Постановка второй задачи

Требуется смоделировать городскую сеть мониторинга климата на базе MQTT:

- **Здания**: несколько зданий в городе, каждое обслуживает один локальный MQTT-брокер.
- **Этажи**: в каждом здании от 3 до 10 этажей.
- **Датчики**: на каждом этаже датчики температуры, влажности, CO2, давления (от 4 до 20 датчиков на этаж).
- **Сети здания**: несколько коммутаторов узлов (разные сети на разных этажах или зонах здания), кабель / Wi-Fi / Ethernet.
- **Городская сеть**: здания связаны в городскую сеть через коммутаторы и маршрутизаторы.
- **Центральный городской брокер**: агрегирует данные со всех зданий города.
- **Связь центральных брокеров**: несколько центральных брокеров связаны между собой для отказоустойчивости (резервирование, балансировка нагрузки).

Цель моделирования: оценить доставку климатических данных, задержку, сетевой трафик и устойчивость городской IoT-сети при разных топологиях связи между зданиями и центральными брокерами.

---

## 12. Архитектура системы

```
Здание A (этажи 1–N, датчики Т/влажн/CO2/давл.) → Брокер здания A → Коммутатор района → Центральный брокер города 1
Здание B (этажи 1–M, датчики Т/влажн/CO2/давл.) → Брокер здания B → Коммутатор района → Центральный брокер города 1
Здание C ...                                                                → Центральный брокер города 2
Здание D ...                                                                → Центральный брокер города 2
                                                              ↕
Центральный брокер города 1 ⇄ Центральный брокер города 2 (отказоустойчивая связь, резервирование)
```

### Компоненты модели

| Компонент | Описание | Количество (пример) |
|-----------|----------|---------------------|
| Датчик климата | IoT-устройство: температура, влажность, CO2, давление, публикует телеметрию | 4–20 на этаж |
| Этаж здания | Группа датчиков на одном этаже, подключена к коммутатору этажа | 3–10 на здание |
| Брокер здания | Локальный MQTT-брокер в здании, агрегирует все этажи здания | 1 на здание |
| Коммутатор здания | Сетевой коммутатор здания, связывает этажи и брокер здания | 1–3 на здание |
| Коммутатор района | Коммутатор района, связывает несколько зданий | 1 на 5–10 зданий |
| Центральный брокер города | Агрегирует данные со всех зданий района/города | 1 на город/район |
| Связь центральных брокеров | Канал отказоустойчивости между городами/районами | Ring / Mesh / Federation |

### Связи

- Датчик → Коммутатор этажа: локальная сеть этажа (Ethernet / Wi-Fi, QoS 0/1/2)
- Коммутатор этажа → Брокер здания: внутренняя сеть здания
- Брокер здания → Коммутатор района: канал здания-квартала
- Коммутатор района → Центральный брокер города: канал города
- Центральный брокер города ⇄ Центральный брокер города: резервный канал отказоустойчивости

---

## 13. Топологии для моделирования в MqttY

### 13.1 Star (звезда) — здания через один центральный брокер города

Все брокеры зданий подключаются к одному центральному брокеру города. Центральных брокеров может быть несколько, но каждый обслуживает свою группу зданий.

```
Здание 1 → Центральный брокер города 1
Здание 2 → Центральный брокер города 1
Здание 3 → Центральный брокер города 2
Здание 4 → Центральный брокер города 2
Центральный брокер города 1 ⇄ Центральный брокер города 2
```

**Когда использовать:** мало городов/районов (2–4), чёткое разделение по географии.

### 13.2 Ring (кольцо) — центральные брокеры в кольце

Центральные брокеры соединены в кольце. Данные могут идти по часовой или против часовой стрелки. При выходе одного центрального брокера из строя данные перенаправляются через обратное направление.

```
Центральный брокер 1 → Центральный брокер 2 → Центральный брокер 3 → Центральный брокер 4 → Центральный брокер 1
```

**Когда использовать:** отказоустойчивость важнее задержки, 3–6 центральных брокеров.

### 13.3 Line (линия) — центральные брокеры в цепочке

Центральные брокеры соединены цепочкой. Крайние брокеры имеют по одному соседу, внутренние — по два.

```
Центральный брокер 1 → Центральный брокер 2 → Центральный брокер 3 → Центральный брокер 4
```

**Когда использовать:** линейная география города (например, вдоль главной улицы или реки).

### 13.4 Mesh (полносвязная сеть) — все центральные брокеры связаны

Каждый центральный брокер соединён с каждым. Максимальная отказоустойчивость, но наибольший трафик.

```
Центральный брокер 1 ⇄ Центральный брокер 2 ⇄ Центральный брокер 3 ⇄ Центральный брокер 4 (все со всеми)
```

**Когда использовать:** критически важные климатические данные, бюджет на трафик не ограничен.

### 13.5 Federation (статическая федерация) — MqttY Federation engine

Центральные брокеры работают как федераторы с подавлением повторов. Каждый город обслуживает свои здания, а межгородская доставка идёт через федераторов с кэшем ID и hop-limit.

**Когда использовать:** много городов/районов (до 16 в MqttY Federation), нужно подавление дублей и контроль трафика.

## 15. Ожидаемые цифры и метрики

### 15.1 Нагрузка (MqttY: M = R × T)

При 800 датчиках, частоте 0.05 Гц, времени измерения 60 с:

```
M = 800 датчиков × 0.05 сообщений/с × 60 с = 2400 сообщений
```

При QoS 1 (4 пакета на путь) и длине пути 3 (датчик → этаж → здание → город):

```
X ≈ 4 × M × (L+1) ≈ 4 × 2400 × 4 = 38 400 пакетов (только датчики → центральный брокер)
```

При межгородской связке (Federation star, B=4):

```
X_fed ≈ M × (8.08×B² − 11.98×B + 11.84) ≈ 2400 × 117.5 ≈ 282 000 пакетов
```

### 15.2 Доставка (D)

| Топология | D / M | Комментарий |
|-----------|-------|-------------|
| Датчик → Центральный брокер (Star, идеальный канал) | ~100 % | Надёжный городской канал |
| Датчик → Центральный брокер (Wi-Fi, потери 1 %) | ~99 % | Потери на беспроводном канале этажа |
| Город → Город (Ring, Federation) | ~99.5–100 % | Надёжный межгородской канал |
| Город → Город (при отказе одного центрального брокера) | ~85–95 % | Перенаправление через альтернативный город |

### 15.3 Задержка (p99)

| Составляющая | Задержка | Комментарий |
|--------------|----------|-------------|
| Датчик → Коммутатор этажа (Wi-Fi/Ethernet) | 5–50 мс | Внутренняя сеть здания |
| Коммутатор этажа → Брокер здания | 2–20 мс | Внутренняя сеть здания |
| Брокер здания → Центральный брокер города | 10–100 мс | Городская сеть |
| Центральный брокер города → Центральный брокер города | 20–200 мс | Межгородской канал |
| **Итого (до центрального брокера своего города)** | **30–250 мс** | p99, в зависимости от QoS и потерь |
| **Итого (с отказоустойчивой пересылкой между городами)** | **60–450 мс** | +1–2 дополнительных hop |

## 20. Резюме суммарной статьи

Архитектура «Поле/Здание → Брокер узла → Региональный/Центральный брокер → Связанные брокеры» моделируется в MqttY с использованием Federation engine и топологий Star/Ring/Line/Mesh. Ожидается, что:

- **Star** проще реализовать, но имеет единственную точку отказа на уровне региона/города.
- **Ring** даёт хороший баланс трафика и отказоустойчивости для 3–6 узлов верхнего уровня.
- **Mesh** максимизирует отказоустойчивость, но увеличивает трафик O(B²).
- **Federation** подходит для до 16 узлов верхнего уровня с подавлением дублей и контролируемым трафиком.

Для сельскохозяйственных IoT-полей с плохим мобильным каналом рекомендуется комбинация **Ring** между региональными брокерами (отказоустойчивость) и **QoS 1** на каналах поля (баланс надёжности и накладных расходов).

Для городской сети IoT климата с хорошими внутренними сетями зданий рекомендуется комбинация **Federation** между центральными брокерами городов (подавление дублей, контроль трафика) и **QoS 1/2** внутри зданий (высокая надёжность климатических данных).
