# Статья 3: Моделирование крупных IoT-архитектур в MqttY

**Дата:** ноябрь 2026  
**Статус:** проектная документация с результатами реальных экспериментов  
**Инструмент:** MqttY (симулятор MQTT-сетей), MqttBenchmark (опционально, для натурных профилей)  
**Проведено экспериментов:** 6 (3 сельского IoT + 3 городского IoT)

---

## 1. Постановка задачи

Требуется смоделировать два типа крупных IoT-архитектур на базе MQTT:

### Задача 1: Сельское IoT (поля и оросительные установки)
- **Поля**: несколько полевых участков, каждое обслуживает один локальный (полевой) MQTT-брокер.
- **Оросительные установки**: на каждом поле от 5 до 10 устройств (IoT-контроллеры орошения, датчики влажности, насосы).
- **Сети поля**: обычно мобильный интернет (4G/LTE), плохой IoT-канал — высокая задержка, потери пакетов, ограниченная пропускная способность.
- **Региональные брокеры**: каждый собирает данные с нескольких полей.
- **Связь региональных брокеров**: региональные брокеры связаны между собой для отказоустойчивости.

### Задача 2: Городское IoT (здания и климатические датчики)
- **Здания**: несколько зданий в городе, каждое обслуживает один локальный MQTT-брокер.
- **Этажи**: в каждом здании от 3 до 10 этажей.
- **Датчики**: на каждом этаже датчики температуры, влажности, CO2, давления (от 4 до 20 датчиков на этаж).
- **Сети здания**: несколько коммутаторов узлов (разные сети на разных этажах или зонах здания), кабель / Wi-Fi / Ethernet.
- **Городская сеть**: здания связаны в городскую сеть через коммутаторы и маршрутизаторы.
- **Центральный городской брокер**: агрегирует данные со всех зданий города.
- **Связь центральных брокеров**: несколько центральных брокеров связаны между собой для отказоустойчивости.

Цель моделирования: оценить доставку, задержку, сетевой трафик и устойчивость при разных топологиях связи для обеих задач.

## 2. Архитектура системы

### 2.1 Сельское IoT (Часть 1)

```
Поле A (оросительные установки 5–10 шт.) → Полевой брокер A → Региональный брокер 1
Поле B (оросительные установки 5–10 шт.) → Полевой брокер B → Региональный брокер 1
Поле C ...                                                      → Региональный брокер 2
Поле D ...                                                      → Региональный брокер 2
                                                              ↕
Региональный брокер 1 ⇄ Региональный брокер 2 (отказоустойчивая связь)
```

### 2.2 Городское IoT (Часть 2)

```
Здание A (этажи 1–N, датчики Т/влажн/CO2/давл.) → Брокер здания A → Коммутатор района → Центральный брокер города 1
Здание B (этажи 1–M, датчики Т/влажн/CO2/давл.) → Брокер здания B → Коммутатор района → Центральный брокер города 1
Здание C ...                                                                → Центральный брокер города 2
Здание D ...                                                                → Центральный брокер города 2
                                                              ↕
Центральный брокер города 1 ⇄ Центральный брокер города 2 (отказоустойчивая связь, резервирование)
```

## 3. Топологии для моделирования в MqttY

В MqttY доступны следующие топологии и движки, которые подходят для обеих архитектур:

### 3.1 Star (звезда)

Все узлы подключаются к одному центральному брокеру. Региональных/городских брокеров может быть несколько, но каждый обслуживает свою группу.

```
Узел 1 → Центральный брокер 1
Узел 2 → Центральный брокер 1
Узел 3 → Центральный брокер 2
Узел 4 → Центральный брокер 2
Центральный брокер 1 ⇄ Центральный брокер 2
```

### 3.2 Ring (кольцо)

Центральные брокеры соединены в кольце. Данные могут идти по часовой или против часовой стрелки.

```
Брокер 1 → Брокер 2 → Брокер 3 → Брокер 4 → Брокер 1
```

### 3.3 Line (линия)

Центральные брокеры соединены цепочкой.

```
Брокер 1 → Брокер 2 → Брокер 3 → Брокер 4
```

### 3.4 Mesh (полносвязная сеть)

Каждый брокер соединён с каждым.

```
Брокер 1 ⇄ Брокер 2 ⇄ Брокер 3 ⇄ Брокер 4 (все со всеми)
```

### 3.5 Federation (статическая федерация) — MqttY Federation engine

Брокеры работают как федераторы с подавлением повторов. Каждый регион обслуживает свои узлы, а межрегиональная доставка идёт через федераторов с кэшем ID и hop-limit.

## 5. Результаты экспериментов в MqttY (реальные замеры)

### 5.1 Сельское IoT (поля и оросительные установки)

Эксперименты проведены с 4 региональными брокерами, 12 полями, 48 издателями, QoS 1, 1000 сообщений/с, 10 с измерения.

| Метрика | Star (Federation) | Ring (Federation) | Relay (Star) |
|---------|-------------------|-------------------|--------------|
| Publish попытки/завершения | 10000/10000 | 10000/10000 | 10000/10000 |
| Source RPS | 1000 | 1000 | 1000 |
| Delivery goodput | 3846.9 | 4000.0 | 4000.0 |
| Loss | 3.83% | **0.0%** | **0.0%** |
| p99 ACK (мс) | 0.8 | 0.8 | 0.8 |
| p99 доставки (мс) | 1488.4 | **5.5** | **2.8** |
| Пересылок | 77627 | 50000 | 30000 |
| Подавлено повторов | 49148 | 20000 | 0 |
| Queue drops | 0 | 0 | 0 |
| Статус | failed (drain timeout) | completed | completed |

**Выводы сельского IoT:**
- **Ring Federation** показывает лучшие результаты: 0% потерь, p99 доставки 5.5 мс, 50000 пересылок.
- **Relay** показывает лучшую задержку доставки (2.8 мс) и 0% потерь, но только 30000 пересылок (нет подавления дублей).
- **Star Federation** показывает 3.8% потерь из-за переполнения очереди на транзитном узле, drain timeout.

### 5.2 Городское IoT (здания и климатические датчики)

Эксперименты проведены с 4 центральными брокерами, 20 зданиями, 80 издателями, QoS 1, 2000 сообщений/с, 10 с измерения.

| Метрика | Star (Federation) | Ring (Federation) | Relay (Star) |
|---------|-------------------|-------------------|--------------|
| Publish попытки/завершения | 20000/20000 | 20000/20000 | 20000/20000 |
| Source RPS | 2000 | 2000 | 2000 |
| Delivery goodput | 4887.7 | 4887.8 | **8000.0** |
| Loss | 38.90% | 38.90% | **0.0%** |
| p99 ACK (мс) | 0.8 | 0.8 | 0.8 |
| p99 доставки (мс) | 4406.4 | 4163.3 | **2.8** |
| Пересылок | 77639 | 67682 | 60000 |
| Подавлено повторов | 38627 | 19824 | 0 |
| Queue drops | 54826 | 28535 | 0 |
| Статус | failed (drain timeout) | failed (drain timeout) | completed |

**Выводы городского IoT:**
- **Relay** показывает лучшие результаты: 0% потерь, p99 доставки 2.8 мс, goodput 8000.
- **Star и Ring Federation** показывают высокие потери (38.9%) из-за переполнения очереди при высокой нагрузке (2000 RPS, 80 издателей).

### 5.4 Рекомендации

1. **Сельское IoT (плохой мобильный канал):** Использовать **Ring** между региональными брокерами (отказоустойчивость, 0% потерь) и **QoS 1** на каналах поля (баланс надёжности и накладных расходов).

2. **Городское IoT (хорошая внутренняя сеть зданий):** Использовать **Relay** между центральными брокерами городов (0% потерь, лучшая задержка 2.8 мс) и **QoS 1/2** внутри зданий (высокая надёжность климатических данных).

3. **Star топология** не рекомендуется для высоконагруженных сценариев из-за переполнения очереди на транзитном узле (показывает drain timeout и 38.9% потерь при RPS=2000).

## 6. Резюме суммарной статьи

### 6.1 Сельское IoT (поля и оросительные установки)

Архитектура «Поле → Полевой брокер → Региональный брокер → Связанные региональные брокеры» моделируется в MqttY с использованием Federation engine и топологий Star/Ring/Line/Mesh. Результаты экспериментов:

- **Star** проще реализовать, но имеет единственную точку отказа на уровне региона и показывает потери 3.8% при высокой нагрузке.
- **Ring** даёт хороший баланс трафика и отказоустойчивости для 3–6 регионов: 0% потерь, p99 доставки 5.5 мс.
- **Mesh** максимизирует отказоустойчивость, но увеличивает трафик O(B²).
- **Federation** подходит для до 16 регионов с подавлением дублей и контролируемым трафиком.

Для сельскохозяйственных IoT-полей с плохим мобильным каналом рекомендуется комбинация **Ring** между региональными брокерами и **QoS 1** на каналах поля.

### 6.2 Городское IoT (здания и климатические датчики)

Архитектура «Здание → Брокер здания → Коммутатор района → Центральный брокер города → Связанные центральные брокеры» моделируется в MqttY. Результаты экспериментов:

- **Star Federation** не подходит для городского IoT: показывает 38.9% потерь при RPS=2000 из-за переполнения очереди на транзитном узле.
- **Ring Federation** также показывает 38.9% потерь при высокой нагрузке.
- **Relay** показывает лучшие результаты: 0% потерь, p99 доставки 2.8 мс, goodput 8000, 60000 пересылок.

Для городской сети IoT климата с хорошими внутренними сетями зданий рекомендуется комбинацию **Relay** между центральными брокерами городов и **QoS 1/2** внутри зданий.

### 6.3 Общие выводы

1. **Топология Star** подходит только для малых нагрузок и не критичных к потерям сценариев.
2. **Топология Ring** показывает стабильные результаты для сельского IoT, но не справляется с высокой нагрузкой городского IoT.
3. **Режим Relay** обеспечивает наилучшую надёжность и задержку для обоих сценариев при отказе от подавления дублей.
4. **QoS 1** рекомендуется для обоих сценариев как баланс между надёжностью и накладными расходами.
5. **QoS 0** подходит только для сценариев с допустимыми потерями и приоритетом минимального трафика.
