# Короткие технические опыты для первой статьи

Выполнены реальные короткие запуски, необходимые для подготовки новой проверки. **Они не доказывают точность двойника Mosquitto:** натурная часть проверяет независимый небольшой MQTT-клиент, модельная — политику нагрузки идеального брокера. Эти две части нельзя подставлять в одну таблицу «оригинал — двойник».

## Настоящий Mosquitto на Linux

Запущен отдельный процесс `/usr/sbin/mosquitto` с собственной временной конфигурацией: случайный свободный порт, только loopback, без постоянного хранилища. Контрольная сумма исполняемого файла: `34cee46d71bd97aca34c75fcb844674ab787434468c06423a3a1f2825a213dea`.

Независимый клиент написан на стандартной библиотеке Python. Он исполняет MQTT 3.1.1: CONNECT/SUBSCRIBE, для QoS 1 — PUBLISH/PUBACK, для QoS 2 — PUBLISH/PUBREC/PUBREL/PUBCOMP. Для подписчика также исполняется обмен выбранного QoS. Пакеты и ID заданы явно; библиотека MqttBenchmark в этом техническом опыте не используется.

На каждый QoS заранее назначено 100 разных ID в сообщениях по 16 байт. Одно сообщение подаётся каждые 20 мс в двухсекундном окне. Все времена имеют общее монотонное начало. После окна учитываются поздние получения.

| Проверяемая величина | QoS 1 | QoS 2 |
| --- | ---: | ---: |
| Задано сообщений | 100 | 100 |
| Попыток | 100 | 100 |
| Успешных завершений | 100 | 100 |
| Уникальных получений | 100 | 100 |
| Неуспешных / незавершённых | 0 / 0 | 0 / 0 |
| Дубликатов | 0 | 0 |
| Первых получений во время ожидания | 0 | 1 |
| Фактический размер каждого сообщения | 16 байт | 16 байт |

Получено заданное число сообщений; контрольные суммы скачанных raw совпадают, отдельный локальный пересчёт воспроизвёл все опубликованные поля. Единственное получение QoS 2 после границы подачи показывает, зачем отдельно учитывать ожидание. Значение RPS 50/с здесь задано расписанием, а не является измеренной предельной производительностью брокера. Сто наблюдений недостаточно для уверенного вывода об устойчивости p99.

Служба `mqtty-article1-native-micro-v1.service` завершилась успешно за 4,493 с. В выводе systemd-run: CPU 233 мс, пик памяти 13,2 МиБ. Ограничения службы: CPUQuota=100%, MemoryMax=512M, RuntimeMaxSec=120, один последовательный исполнитель. Собственный брокер PID 126824 завершён штатно, MainPID службы после выполнения равен нулю. Службы основной сети и Web не останавливались; контрольный ответ `/healthz` Web был успешным.

Удалённые данные: `/run/media/entityfx/hd250/mqtty-evidence/article1-native-micro-v1/attempt-001`. Компактные raw и локальный пересчёт сохранены в `reports/audits/dissertation/article-1-compact-readiness-v1/native-linux/`.

## Модельный цикл без подстановки измеренного RPS

В существующий интеграционный тестовый проект добавлен `ClosedLoopBudgetMicroTests`. Рабочее ядро модели не менялось. Для QoS 1 и 2 выполнено по три симуляции: ограничение 10 публикаций/с, потолок 40 000 и удвоенный потолок 80 000.

Параметры: идеальный одиночный брокер, четыре отправителя, один получатель, 16 байт, tick 0,1 мс, прогрев 100 ticks, нагрузка 2000 ticks, ожидание до 10 000 ticks, seed 42. Значение 40 000 вычислено как число отправителей / tickSeconds и не получено из натурного результата.

| Показатель | QoS 1 | QoS 2 |
| --- | ---: | ---: |
| Завершений при потолке 10/с | 2 | 2 |
| Завершений при потолке 40 000/с | 1140 | 616 |
| Завершений при потолке 80 000/с | 1140 | 616 |
| Совпадают все поля научной сводки двух высоких потолков | Да | Да |

Низкое ограничение действительно меняет нагрузку. В проверенных двух точках удвоение высокого потолка не меняет результат: можно убрать зависимость от **нового натурного** RPS, задав потолок по параметрам симуляции. Это локальный технический результат для идеальной модели, а не доказательство свойств всех профилированных режимов. Квантование по tick и очередь обработки остаются частью модели.

Два параметризованных теста прошли; время test run — 7,329 с, непосредственно тесты — около двух и одной секунды. Дополнительно прошли три проверки кодирования независимого MQTT-клиента. Ранее прошли девять проверок нового пересчёта и 14 регрессионных проверок старого аудита. Итого проверено 28 тестовых случаев, без новых изменений порогов оценки.

## Что это закрывает и что ещё нужно

Закрыты два конкретных подготовительных вопроса: при малой заданной нагрузке можно получить проверяемые уникальные сообщения с точным учётом фаз; токеновый потолок модели можно проверить без обратной подстановки нового измерения.

Точная граница подачи и состояния соединений добавлены в MqttBenchmark; журнал ID и исходов публикаций — в одиночную модель MqttY. Реальные и профилированные пилоты выполнены, программа 48+48 и входы зафиксированы. Новая серия запущена на Linux с суммарным лимитом продолжения 6 часов; подтверждения и состояние указаны в `reports/status/Progress.md`. Текущие восемь технических запусков сами по себе не закрывают сравнительную серию. Исторические результаты, замороженные профили, runtime основной сети и допуски не изменены.

Статья готова как рабочая рукопись, но окончательный вывод о точности новой проверки пока не готов. После серии необходимо проверить все 48 пар, точные временные окна, прогрев, отключения, знаменатели недоставки и завершения во время ожидания. Показать каждый натурный повтор и модельный результат; усреднение не должно скрывать провалы. Проверка короткого окна относится к выбранной нагрузке и не доказывает предельную производительность или точность во всех режимах.

Web технически проверен для модельных серий MqttRelay, федерации и балансировщика (9 опытов и 3 повтора). Эта проверка не доказывает, что внешняя серия MqttBenchmark + одиночный BrokerFidelity запускается из Web: она выполняется отдельным контроллером, в очереди Web не отображается.

## Повтор после диагностики EMQX

Отказы первой полной серии вызваны началом измерения до готовности MQTT в EMQX. Пилот подтвердил 22 сброса соединения после открытия TCP, затем успешный CONNACK и 20 153 завершения без недоставки. На Linux запущен повтор 12 недостающих натурных точек; все готовые модели сохраняются. Подробности и предварительный разбор остальных расхождений — в `reports/analysis/Article-1-emqx-recovery.md`. Проверка арифметики первой таблицы подтвердила 53 показателя в допуске и 91 вне допуска; это не подтверждение точности модели. Приёмка новых результатов ещё предстоит.
